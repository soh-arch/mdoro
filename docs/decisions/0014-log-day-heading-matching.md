# 0014. ログの日付見出しは、日付が読めれば同一の見出しとみなす

- **状態**: accepted
- **日付**: 2026-08-26

## 文脈

工程3（Obsidian 連携）の実装中に、REQ-LOG-003 と REQ-LOG-022 が特定の入力で逆の指示を出すことが判明した。

- **REQ-LOG-003**: 「当該見出しが既に存在する場合は、その日付セクションの末尾へ追記する」
- **REQ-LOG-022**: 「当日の見出し行が外部で削除・**改名**されていた場合は、見出しを再作成して**ファイル末尾**に追記する」

食い違うのは「見出しの日付は合っているが、見た目が変えられている」場合だけである。
たとえばユーザーが `## 2026-08-24 (月)` を `## 2026-08-24 (Mon)` に書き換えていたとき、
003 は既存節への追記を、022 は末尾への新設を指示する。

見出しが完全一致する場合と、見出しごと消えている場合は、両条文とも同じ結論になる。

## 判断

**`## ` の直後に当該論理日の `YYYY-MM-DD` が現れれば、同一の見出しとみなして既存節の末尾へ追記する。**

- 曜日部分の表記が変えられていても「改名」には当たらない。REQ-LOG-022 の再作成経路には進まない。
- 行の途中に日付を含むだけの見出し（例: `## 週次レビュー 2026-08-24 の分`）は当該見出しではない。
  見出しを新設し、ファイル末尾へ追記する。
- 見出しを書き換えることはしない。ユーザーが変えた表記はそのまま残す。

## 理由・設計意図

**条文どおりに「改名されていたら末尾へ」を実装すると、同じ日の見出しが2つ並び、記録が分断される。**

```markdown
## 2026-08-24 (Mon)      ← ユーザーが書き換えた見出し
- 09:00–09:25 WORK ...

## 2026-08-24 (月)       ← アプリが作り直した見出し
- 09:32–10:04 WORK ...
```

曜日を英語で書くのがそのユーザーの習慣なら、これが毎日起きる。
第7章の目的は「振り返り」であり（7.3 背景・理由）、記録が日ごとに二分される状態はその目的を直接損なう。

REQ-LOG-022 の力点は前半の「改名されていたら末尾へ」ではなく、**後半の「既存の行を復元・修正しようとしてはならない」**にある。
この条文が防いでいるのは、見出しが見つからないときにアプリが賢く振る舞おうとしてユーザーのファイルを直しにいくことである。
日付が読める見出しを見つけてその下に足す動作は、この禁止に当たらない。既存行には一切触れないためである。

**この判断はデータの安全性とは無関係である。** どちらを選んでも `LogFileEditor` の検査により既存行は1行も変わらない
（[0002](0002-task-md-read-only.md)）。変わるのは新しい行がどこに入るかと、ファイルの見た目だけである。
したがって、読みやすさを基準に決めてよい論点だった。

日付の位置を `## ` の直後に限ったのは、緩く照合するとユーザー自身が書いた
`## 週次レビュー 2026-08-24 の分` のような節にログ行を混入させるためである。
