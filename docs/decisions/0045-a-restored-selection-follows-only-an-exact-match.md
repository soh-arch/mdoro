# 0045. 起動をまたぐ追従は、完全一致だけを信じる

- **状態**: accepted
- **決定日**: 2026-09-19
- **決定者**: 人間
- **反映**: コードのみ（`#165`）
- **関連**: [0002](0002-task-md-read-only.md) / [0040](0040-identity-is-not-a-name.md)

## 文脈

`REQ-TSK-032` は選択の追従を**1回の再読み込みの中の出来事**として書いている ——
**消失したタスク**と、**同じ再読み込みで新規に出現したタスク**との間で正規化本文の
Levenshtein 距離を測り、**本文長の 30% 以内**の候補が一意に定まるなら同じタスクとみなす。

**起動時の復元は、その場面ではない。** `AppModel.init` は `TaskContext` を
`items` 既定値の空で組み、その後で最初のパースが走る。**アプリの中に前の一覧が無いので、
「消失したタスク」が観測されない。**追従の基準になる本文が取れず、`#165` の前は
**何もせずに返っていた。**

普通の起動ではこれで困らない。永続化された `stableId` が新しい一覧にまだ在れば、
選択はそのまま残る。**困るのは `stableId` が動いたときである。**

`stableId` は正規化本文のハッシュである（`REQ-TSK-021`）。
**つまり、正規化の答えを変えるのは利用者ではなく私たちである。**
POL-273 は実際に変えた（旗・絵文字直後の結合文字）。**利用者が `Task.md` を1文字も編集していなくても、
私たちの新しい版が、その利用者の選択を黙って外す。**これが POL-291 だった。

## 判断

1. **復元の経路でも追従する。ただし正規化本文が完全に一致したときだけとする。許容距離は 0。**
2. **一覧が在るときの 30% は変えない。**式も数値も、1行も触らない。
3. **照合の基準は、永続化された `selectedTaskSnapshot`（`displayText`）を
   `TaskTextNormalizer.normalize(body:)` に通したものとする。**
4. **`REQ-TSK-032` の条文は変えない。この判断の記録はこのレコードだけである。**

## 理由・設計意図

**人間の理由がこの判断の本体である。**

> 閉じているあいだに削除・改名したなら、選択が外れて納得がいく。
> 読み取り専用で、行番号で追っているわけでもない道具なら、利用者はそう読む。
> **一致しないタスクを「あなたが選んでいたものです」という顔で出すほうが不信を買う。**

**ログに何が残るかより手前の、信用の問題である。**
外れた選択は、利用者が自分の操作として説明できる。**間違って付いた選択は説明できない。**

**機械の側の理由は、30% という数字の出どころにある。**
あの数字は「**候補が、新しく出てきた行だけである**」という証拠とセットで決まった。
消えた1行と現れた1行が向かい合っているから、多少の距離を許しても取り違えない。
**復元にはその証拠が無い。**前の一覧が無いので、**ファイルの全行が候補になる。**
**証拠を外して、許容だけを持ち越さない。**

**照合の基準が近似であることは承知のうえである。**
`displayText` は絵文字除去と NFKC を通っていないので、正規化を2度通すとその2段だけが効く。
⚠ **食い違えば距離が増える方向にしか動かない。**完全一致の下で距離が増えれば「追従しない」——
**`#165` の前の挙動に落ちるだけである。取り違えの方向には倒れない。**

**条文にしない理由は、これが天秤の取り方であって定理ではないからである**（`CLAUDE.md`）。
条文に「復元では 0」とだけ書けば、次に読む人は **30% と 0 の不一致を「揃えるべき矛盾」と読む。**
**守りたいのは数字ではなく、「証拠の無い追従はしない」という向きである。**
向きは条文の書式に乗らない。**レコードの仕事である。**

## 影響

- **`REQ-TSK-032` / `REQ-TSK-035`**: 字面は変えない。**守備範囲は「同じ再読み込みの中」のままである。**
  ⚠ **復元の経路はその外側にあり、根拠はこのレコードだけである。**条文だけを読んで実装する人には届かない。
  **これは (a) 条文を足す・(b) レコードを起こす・(c) 何もしない の三択で (b) を選んだ結果であり、承知の残余である。**
- **`REQ-TSK-021`**: `stableId` が正規化本文のハッシュであることが、この問題の入口である。
- **`REQ-PER-001` / `REQ-PER-002`**: 何を永続化し、何を復元するか。
- ⚠ **データモデルの `selectedTaskSnapshot` は「消失時の表示・ログ記録用」と2つの用途を書いている**
  （`SPEC.md` 第9章）。**この判断が3つ目の用途を足した。**条文を変えないと決めたので表も変えないが、
  **次に第9章を改訂する人は、ここを見てから書く。**
- **コード**: `Packages/MdoroCore/Sources/MdoroCore/Tasks/TaskContext.swift` の
  `FollowReference` と `followReference(in:selectedId:)`。**基準と許容距離を1つの型に束ねた**ので、
  一覧が在る経路の式は数値も含めて同一である。
  ⚠ **コードのコメントは、この判断の理由をすでに現場に書いている**（`followReference(in:selectedId:)` の直上、
  30% の値付けの話も、信用の話も）。**このレコードへの参照は入れていない** —— Swift に触れば
  所有者の Mac でのビルドが1回要るので、**コメント1行のために手を借りる釣り合いにならない。
  次に `TaskContext.swift` を触る便で足す。**
- ⚠ **「控えめな通知」（`REQ-TSK-032` の2文目）は、復元の追従でも出る。**
  同じ `TaskReloadOutcome` を返しているので `didFollow` が立ち、Mac の一覧に
  `Followed the selection` が現れる（`Views/TaskListView.swift`）。
  **条文がそう命じたからではなく、型を共有した結果である。**
  **起動直後にこれが出るのが利用者にとって自然かは、検討していない。**
- ⚠ **本文が同じで完了状態だけが違う2行には、いまも届きうる。**距離0の同点は先勝ちなので、
  **完了済みを選んでいたのに未完了のほうが返ることがある。**
  **永続化しているのは id と本文だけで状態を持っていないので、見分ける材料がそもそも無い。直さない。**

## 出典と確度

- **事実**: `REQ-TSK-032` の「同じ再読み込みで」「本文長の 30% 以内」、`REQ-TSK-035` が
  `REQ-TSK-032` を名指していることは、`SPEC.md` の条文そのもの。
- **事実**: 起動時に前の一覧が空であること、`reloadTasksFromDisk()` が `TaskReloader.reload` を
  呼ぶことは、`AppModel.swift` / `TaskContext.swift` を読んで確認（2026-09-18）。
- **事実**: 実装が所有者の Mac でコンパイルされ、走るテストが通ったことは `#165`（2026-09-19）。
- **判断**: 完全一致だけを信じることは**人間の決定**であり、推測ではない。
  **条文ではなくレコードに残すことも人間の決定である**（2026-09-19）。
- ⚠ **未検討**: 起動直後に `Followed the selection` が出ることの是非。
