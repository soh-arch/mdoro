# 0029. メニューバーを操作面にする（ウィンドウ依存を減らす）

- **状態**: accepted
- **日付**: 2026-08-28

## 文脈

REQ-UIX-031 は、メニューバーのドロップダウンから提供する操作を4つに絞っていた。
中断・リセット・プリセット編集・設定変更は**誤操作防止**のためメインウィンドウ専用としていた。

工程11 の実機確認で、プロダクトオーナーから意図の提起があった。

> md でタスクを管理するような、簡潔を大切にするパワーユーザーを想定しているので、
> **ウィンドウ操作のみで機能する動作を減らすべき。**
> ホットキーを設けたように、より簡潔な別の操作でも補えるようにすべき。

**ウィンドウを開くことが、操作の前提になっていた。**

## 判断

**メニューバーを、ウィンドウの代わりに使える操作面にする。**
ただし**誤操作防止は捨てない。** 危険度で階層を分ける。

| 層 | 置くもの | 根拠 |
| :---- | :---- | :---- |
| **メニュー直下** | 一時停止 / 再開、次を開始、**スキップ**、プリセット切替、**設定を開く**、メインウィンドウ、終了 | どれも取り返しがつく。スキップは周回数を減らさない（4.5） |
| **確認を1段はさむ** | **中断**、**周回リセット** | 破壊的。滑って押しても走らない |
| **サブメニュー** | **タスク選択**、**外観**、**メニューバーの表示密度** | 設定画面の一部。選ぶだけで、破壊的操作を含まない |
| **置かない** | プリセットの編集、ファイルのパス変更、ペアリング | **不可逆か、外の世界に触る** |
| **ホットキー** | 従来の2つに加えて **次を開始 / スキップ** | 既定は未割り当て（REQ-UIX-033 の作法） |

## 理由・設計意図

**旧条文が守っていたのは「誤操作」であって、「メニューにあること」ではない。**
破壊的な操作が浅い場所にあると、狙っていないのに走る。
しかし**「浅い場所」と「メニューにある」は同じではない。** 確認を1段はさめば、深さは作れる。

**対象読者を考えると、ウィンドウ依存そのものが摩擦である**（[0021](0021-published-as-oss-named-mdoro.md)）。
キーボードとメニューバーで完結する道具に、GUI を経由させる必然性はない。

**置かないものの基準は「取り返しがつくか」ではなく「外に触れるか」。**
プリセットの編集・パスの変更・ペアリングは、**アプリの外にある資産や他の端末に及ぶ。**
狭い縦長のメニューで扱う形ではない。

## 影響

| 対象 | 内容 |
| :---- | :---- |
| REQ-UIX-031 | 全面的に書き換え。4操作の制限 → 危険度による階層 |
| REQ-UIX-033 | ホットキーの対象に「次を開始」「スキップ」を追加 |
| 9.3 | `startNextHotKey` / `skipHotKey` を追加（既定 未設定） |
| 実装 | `MenuBarMenuContent`、`HotKeyCenter.Slot`、`AppModel.updateHotKey()`、設定画面 |
