# 0046. リスナーは1プロセスに1本

- **状態**: accepted
- **決定日**: 2026-09-19
- **決定者**: 人間
- **反映**: コードのみ（`MdoroServer.start()` の畳み込みと `AppModel` の `hasStarted`。**どちらも既に在る**）
- **関連**: [0040](0040-identity-is-not-a-name.md) / [platform/0008](../platform/0008-what-three-tests-rest-on.md) / [platform/0015](../platform/0015-when-a-task-runs-again.md)

## 文脈

**「Mdoro のプロセス1つに対して、待ち受けるリスナーは1本、Bonjour の登録も1件」という不変条件が、コードの3箇所で守られている。**

| 場所 | どう守っているか |
| :---- | :---- |
| `MdoroServer.start()` | **先に `stop()` を呼ぶ**（bind の前に畳む） |
| `AppModel.start()` | `hasStarted` で、2度目の呼び出しを断る |
| テスト（`ListenerFoldingTests` ほか） | **「2度目の start は1本目を畳む」**を押さえる |

⚠ **条文が定めているのは「Bonjour で広告すること」までである**（`REQ-COM-002` / `REQ-COM-003`）。
**「1本だけ立てること」は、どの条文にも無い。**

**そして3箇所が、同じことをそれぞれ別の言い方で抱えている。**
**碇を付け替える作業（POL-165 / POL-274）で、`@Suite` の名前2つと回帰テストの文言1つが、
**碇を持たない制約文**になった。指す先が無いからである。

## 判断

**リスナーは1プロセスに1本とする。2本目を立てようとしたら、先に在るものを畳む。**

**`AppModel.start()` は1プロセスに1回だけ成立する。**ただし `stop()` の後の再起動は拒まない
（`REQ-COM-003`: ペアリング画面を開けばサーバーは上がり直す）。**断るのは反復だけである。**

## 理由・設計意図

**2本立つと、利用者から見て何が起きるかが分かっている。実測がある。**

**2026-08-30、所有者の機械で実測した**（POL-114）。
**`MdoroMac` のプロセス2つに対し、`_mdoro._tcp` の登録が5件出ていた**
（インターフェース 1 / 12 / 20 / 21 / 22 に分かれていた）。

**壊れ方の筋はこうである。**

**メインウィンドウを開き直すと `.task` が再び走り、`start()` がもう一度呼ばれる**
（[platform/0015](../platform/0015-when-a-task-runs-again.md)）。
**当時の `start()` は `self.listener` を上書きするだけで、前の listener を畳んでいなかった** ——
**古い listener は生きたまま、その広告も残る。**

**mDNSResponder は、名前が衝突した登録を拒まずに改名する** —— `(2)`、`(3)` と番号を付ける
（[platform/0008](../platform/0008-what-three-tests-rest-on.md) で実測）。
**拒まれないので、2本目は静かに成立する。**

⚠ **そして利用者に出る文言が、実際の原因と正反対になる。**
**iPhone が「別のプロセスの登録」に当たると、そのプロセスはペアリング中ではないので
`pairingModeNotActive` を返す。画面には「Start pairing on your Mac」と出る** ——
**利用者がいましがた済ませたことを、もう一度やれと言われる。**
**出口の無い往復である。**

⚠ **これは [0040](0040-identity-is-not-a-name.md) が「同一性は名前が担わない」と定めた、その同じ穴である。**
**0040 は「どの Mac か」を名前で決めない、と定めた。この記録は「そもそも2つ在る状態を作らない」を定める。**
**別々の層で、同じ失敗を塞いでいる。**

**なぜ条文ではなく記録なのか。**
**条文（`docs/SPEC.md`）は「何を作るか」を定める。**この判断は「**なぜ1本なのか**」であり、
**理由が落ちると、次に読む人が「2本でも動くのでは」と考え直す余地が残る。**
**実測の記憶が残っている場所が要る。**

## 影響

- **`REQ-COM-002` / `REQ-COM-003`**: 字面は変えない。**この記録が、条文の下にある前提を述べる。**
- **コード**: `MdoroServer.start()` の先頭の `stop()`、`AppModel` の `hasStarted`。**どちらも既に在る。**
  **この記録は新しい実装を要求しない。**
- ⚠ **碇の打ち先になる**（POL-274 / POL-275）: `ListenerFoldingTests.swift:69` と
  `StartingTwiceTests.swift` の `@Suite` 名、`MdoroiOSTests.swift` のダイヤル回帰メッセージ。
  **この3箇所は、いま碇を持たない制約文である。**
- ⚠ **`.task` の再実行と噛み合う** —— **ウィンドウを閉じることはシーンの破棄であり、開き直すと `.task` が再び走る**
  （[platform/0015](../platform/0015-when-a-task-runs-again.md)）。**`hasStarted` はそこを受けている。**
  **2026-08-30 の登録5件は、この経路で生まれた。**

## 出典と確度

- **実測**: 2プロセスで登録5件・ペアリング3回とも失敗（2026-08-30・所有者の機械。POL-114）。
- **実測**: mDNSResponder が衝突した登録を改名すること（[platform/0008](../platform/0008-what-three-tests-rest-on.md)）。
- **実測**: 当たった先がペアリング中でないと `pairingModeNotActive` が返り、画面が
  「Start pairing on your Mac」になること（POL-114）。
- ⚠ **この観測は v2.25 より前のものである。** 当時は `GET /info` 用の2本目のリスナーも在り、
  `start()` は前の listener を畳んでいなかった。**どちらも今は違う。**
  **測った症状そのものは、いまのコードでは再現しない。**
  **この記録が残すのは、症状ではなく「2本立つと何が起きるか」のほうである。**
- ⚠ **未検証**: **`id` が TXT に載ったいま、同名が2件並んだ場合に iPhone が正しいほうを選べるかは、確かめていない。**
  **選べるとしても、この判断は変わらない** —— **2本目のリスナーは2つ目のポートでもあり、
  どちらが状態の正本かという問いが残るからである。**
