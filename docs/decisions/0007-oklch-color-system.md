# 0007. カラーシステムを OKLCH で再構築し、セッション3色に絶対輝度の段差を設ける

- **状態**: accepted
- **日付**: 2026-08-24

## 文脈

プロダクトオーナーが最初にカラーパレットを提示していた。Claude（当時の PM）はそれを所与のものとして扱い、
色を保持したまま小さな修正を積む方向で作業していた。

そこへプロダクトオーナーから **「雰囲気を踏襲していれば、かなり大きな変更を行っても問題ない」** と伝えられた。
提示した色そのものに固執する意図はなく、狙っていたのは**紙とインクのような、彩度を抑えた落ち着いた雰囲気**であり、
その雰囲気が保たれるなら色相も構造も作り直してよい、という許可である。

## 判断

パレットを前提から作り直す。

- **OKLCH（知覚的均等色空間）で全トークンを定義する。** hex は算出結果として扱う。
- **各色相を5役に分解する**: `subtle` / `line` / `graphic` / `solid` / `text`。
  単一の「アクセント色」を用途ごとに使い回さない。役ごとに保証されるコントラストを定める。
- **セッション3色を 藍（Ink 235°）/ 青磁（Sage 142°）/ 黄土（Ochre 66°）に再割り当てし、
  色相だけでなく絶対輝度にも段差をつける。**
- 色覚シミュレーション（1型・2型）下での OKLab 距離を計測し、**最小 ΔE 14 以上**を確保する。
- ビューに色リテラルを書かない。役割名（`sessionFocus`, `warning`, `danger`, `textPrimary`）で参照する。

## 理由・設計意図

**全面再設計に踏み切ったからこそ重大な欠陥が見つかった。** 元のパレットには、
2型色覚下で Focus と Long Break が **ΔE 2.9（実質識別不能）**まで接近する問題があった。
小さな修正を積む方向に留まっていたら、この欠陥は発見されないまま実装に入っていた。

色相だけで区別する設計は色覚多様性下で破綻する。**同一明度に揃えると識別できなくなる**ため、
セッション3色にはあえて絶対輝度の段差を持たせている。ここを「揃えたほうが綺麗」と均すと、保証が消える。

5役に分解しているのは、コントラスト保証を役に紐づけるため。**役を取り違えると保証が消える。**
進行リングなど意味を持つ図形は `-graphic`（対背景 3.0 以上、WCAG 1.4.11）、
文字が乗る塗りは `-solid`（4.5 以上）、背景上のテキストは `-text`（4面すべてに対し 4.5 以上）。

役割名で参照するのは、色相の変更がコード変更にならないようにするため。

## 影響

- 要件: REQ-COL-001〜032（8.5 全体）、REQ-COL-020（ΔE の下限）、REQ-COL-022（メニューバーの除外）
- コード: 色トークン定義（未実装）。**ビューに色リテラルを書かないこと**
- 未着手: 色のコントラストと ΔE の自動検証（REQ-COL-020）を `PomodoroCore` のテストとして追加する
- 例外: Live Activity には 8.5 のトークンをそのまま適用しない（REQ-UIX-027）。
  背景がユーザーの壁紙であるため対 `--bg` のコントラスト保証が成立しない
- 参照: 視覚的リファレンス（トークン一覧・コントラスト実測・色覚シミュレーション）は `docs/CONTEXT.md` に URL がある

## 出典と確度

- **事実**: 判断・意図・PM への影響は、旧 `NOTES.md`（2026-08-24 の項）から移送した。
  ΔE 2.9 / ΔE 14.1 の数値、5役の構成、色相角は `NOTES.md` および仕様書 8.5 に記載がある。
- **推測**: なし。

## 付随して得られた指針

**「どこまで変えてよいか」を明示的に許可されたことが、部分最適から脱する契機になった。**
変更の自由度を与えられたら、既存の枠を保とうとせず前提から検証し直すこと。
逆に、自由度が示されていない領域で前提を覆す変更を行う場合は、先に確認すること。
