# 0024. 改名は全範囲で行う

- **状態**: accepted
- **日付**: 2026-08-27

## 文脈

[0021](0021-published-as-oss-named-mdoro.md) でアプリ名を `Mdoro` と決めたとき、
**どこまで改名するか**を OPEN-017 として残していた。

- **(A)** 表示名・README・ドキュメントのみ。内部は `Pomodoro*` のまま（コスト小）
- **(B)** bundle ID・ターゲット名・スキーム・フォルダ名・モジュール名・Bonjour サービス型まで

## 判断

**(B) を採る。改名は全範囲で行う。**

| 対象 | 現在 | 改名後 |
| :---- | :---- | :---- |
| ターゲット / スキーム | `PomodoroMac` / `PomodoroiOS` / `PomodoroWidget` | `Mdoro*` |
| bundle ID | `com.sohta.PomodoroMac` ほか | `com.sohta.Mdoro` ほか |
| 共有モジュール | `PomodoroCore` | `MdoroCore` |
| Bonjour サービス型 | `_pomodoro._tcp` | `_mdoro._tcp` |
| 診断ログの出力先 | `<Library>/Logs/Pomodoro` | `<Library>/Logs/Mdoro` |
| ログファイルの既定名 | `PomodoroLog.md` | `MdoroLog.md`（パスは従来どおり設定可能） |
| リポジトリ / ルートフォルダ | `Pomodoro_Timer` | `Mdoro` |

**移行コードは書かない。** 未リリースであり、再ペアリングと設定のやり直しで足りる。
これを工程9の完了条件に含める。

## 理由・設計意図

**名前が2つあると、そのどちらでもない第三の名前で呼ばれ始める。**
判断の理由は3つとも「読む側の負担」に関わる。

1. **ブランディング** — 表示名だけ `Mdoro` で中身が `Pomodoro*` だと、
   リポジトリを開いた人が最初に見るのは後者である。統一されていない印象は、
   「簡潔で、挙動が透明で、弁えている」という主張と噛み合わない
2. **認知負荷** — 作者自身が2つの名前を頭の中で対応づけ続けることになる
3. **道具とのすれ違い** — 管理システムや AI エージェントは名前で対象を引き当てる。
   `PomodoroCore` と `Mdoro` が同じものを指すという知識は、**毎回どこかで供給し直す必要がある。**
   実際このリポジトリは、名前とパスの一致を前提に運用されている

**やるなら公開前である。** 公開後の改名は、利用者に再ペアリングと再インストールを強いる。
今なら影響を受けるのは作者1人で済む。

**Bonjour サービス型は両端で一致していなければ、そもそも見つからない。**
Mac と iPhone を同時に更新すること。片方だけ変えると「繋がらない」が起きる。

## 影響

| 対象 | 内容 |
| :---- | :---- |
| Xcode | **ターゲット名・bundle ID・スキーム・フォルダ名の変更は人間の操作**（[0013](0013-pbxproj-is-owned-by-xcode.md)）。1回のセッションにまとめて依頼する |
| コード | `import PomodoroCore` の全書き換え、サービス型・Keychain のサービス名・出力先の定数 |
| 署名 | bundle ID が変わるため、**通知の許可は取り直しになる**（`CONTEXT.md` §3「通知には正しい署名が要る」） |
| ドキュメント | `docs/DEVELOPMENT.md` のパス、`CLAUDE.md`、`SPEC.md` 第16章 |
| 工程 | 工程9（`CONTEXT.md` §6） |

## 出典と確度

- **事実**: 2026-08-27 のユーザー決定。理由（ブランディング・認知負荷・道具とのすれ違い）は本人の言による。
- **事実**: bundle ID の変更で通知許可が取り直しになることは、macOS の通知が署名 ID に紐づく
  という既知の挙動による（同 §3 に実機で確認した記録がある）。
