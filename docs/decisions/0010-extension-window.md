# 0010. 延長の起点を終了予定時刻に固定し、受付ウィンドウを設ける

- **状態**: accepted
- **日付**: 2026-08-25

## 文脈

延長操作（[0003](0003-session-model-and-manual-advance.md)）の実装検討中、Claude（当時の PM）から次の提案があった。

> 終了4分後に延長を押すと1分しか伸びない。操作時点を起点にすべきではないか（`max(sessionEndAt, now) + extendSeconds`）。

プロダクトオーナーはこれを**退けた。**

## 判断

- **延長の起点は「終了予定時刻」に固定する。** 押した時刻を起点にしない。
  終了予定 10:00 のセッションを5分延長したら、10:00:10 に押しても 10:00:55 に押しても終了時刻は 10:05 になる。
- **延長を受け付けるのは、終了5分前から終了1分後までとする。** それ以外では受け付けない。
  - `RUNNING`: `sessionEndAt − now ≤ 300`
  - `PAUSED`: `remainingSeconds ≤ 300`
  - `FINISHED`: `now − finishedAt ≤ 60`
  - ウィンドウ外の `extend` は `error`（`code: extendWindowClosed`）を返し、UI 上でもボタンを無効化する
- **`FINISHED` の猶予を5分から1分へ短縮**し、延長受付ウィンドウと一致させる。
- 終了に気づくのが遅れる問題は、**延長の自由度ではなく予告通知の強化で解決する。**
  単一の `preNotifySeconds` を最大2個のトリガ（残り時間指定・経過割合指定）へ拡張する。

## 理由・設計意図

**4分もオーバーしてから延長できてしまうことのほうが、ポモドーロ手法の趣旨に反する。**

ポモドーロは「区切りを設けて時間を意識する」手法である。区切りを見落としたまま作業を続けられる仕組みを
用意するのは本末転倒になる。延長は「まだ集中が続いているから、意識的にもう少し続ける」という判断のための機能であって、
**「気づいたら過ぎていたので埋め合わせる」ための機能ではない。**

一方で「終了に気づかない」こと自体は解決すべき問題である。ただしその解決先は延長ではなく**通知**である。
終了の5分前に知らせる、セッションの80%が経過した時点で知らせる、といった予告を充実させるほうが、
**問題の原因に対して直接的**である。

副次的に、**実装上の不具合が構造的に消えた。** `extendSeconds` を1〜4分に設定すると、
猶予の後半に延長したときに新しい終了時刻が過去になり、延長が無効化される不具合があった。
受付を終了後1分に絞り、`extendSeconds` の下限が1分であることから、延長後の終了時刻が現在より前になることはなくなった。
**手法としての正しさを優先した判断が、結果的に実装の健全性も回復させた。**

## 付随して得られた指針

**便利さより「その手法が何のための道具か」を優先する。**
Claude の当初の提案は、ユーザー体験の不便さだけを見て、手法としての正しさを見ていなかった。
「押した分だけ確実に得られるほうが親切」という発想は、このアプリが何のための道具かを踏まえていない。

仕様を緩める提案をする前に、**その制約は何を守っているか**を検討すること。
不便の原因が別にあるなら、原因側を直す案を併記すること（この件では予告通知の強化がそれにあたる）。
