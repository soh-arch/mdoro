# 0004. タスクIDは Obsidian ブロックID優先＋正規化本文ハッシュのハイブリッドとする

- **状態**: accepted
- **日付**: 2026-08-24

## 文脈

Markdown には行を一意に識別する仕組みがない。しかしこのアプリは、
「セッション開始時に選んでいたタスク」をログに記録し、ファイル再読み込みをまたいで選択を保つ必要がある。

行番号で識別すると、ユーザーが Obsidian 側で行を1つ増やしただけで選択が別のタスクへずれる。
本文そのもので識別すると、誤字を直しただけで選択が消える。

## 判断

`stableId` を次のハイブリッドで決める。

1. 行末に Obsidian のブロックID（`^abc123`）があれば、それを採用する（種別: `blockId`）。
2. なければ、**正規化した本文の SHA-256 先頭16桁 ＋ 同一ハッシュ内での出現順**を採用する（種別: `contentHash`）。

正規化は次の順で行う。(1) リストマーカーとチェックボックスを除去 → (2) 前後の空白を除去 →
(3) 内部リンク・外部リンクを表示テキストへ置換 → (4) タグ・絵文字・強調記号を除去 →
(5) 連続する空白を単一スペースへ統合 → (6) Unicode 正規化（NFKC）。

ID の種別は `TaskItem` に保持し、UI 上でブロックIDを持つタスクを識別できるようにする。

## 理由・設計意図

**識別の強度をユーザーが選べるようにする。** ブロックIDを付ける操作は Obsidian 側の手間だが、
付ければ文言を変えても選択が維持される。付けなければ本文ベースのゆるい識別になる。
アプリ側が `Task.md` に書き込んでブロックIDを自動付与することは [0002](0002-task-md-read-only.md) により禁じられているため、
この選択は必然的にユーザーの手に委ねられる。

正規化を6段階も定めているのは、装飾の差だけで別タスク扱いになるのを避けるため。
NFKC を最後に置くのは、全角・半角や合成文字の揺れを吸収するため。

「同一ハッシュ内での出現順」を足しているのは、同じ本文のタスクが複数行あっても衝突しないようにするため。

## 影響

- 要件: REQ-TSK-020〜024、仕様書 6.3・6.4
- コード: タスクパーサ（未実装）
- 派生: ログには `selectedTaskSnapshot`（セッション開始時点のスナップショット）を記録する。
  → [0010](0010-extension-window.md) と同じく「実際に作業していたもの」を記録するという原則
- UI: ブロックIDを付けると選択が維持される旨の案内を設定画面かヘルプに出す（REQ-TSK-024, SHOULD）

## 出典と確度

- **事実**: REQ-TSK-020〜024 に条文として存在する。正規化の6段階も条文どおり。
- **推測**: 「識別の強度をユーザーが選べるようにする」という意図の言語化は、
  REQ-TSK-023（種別を UI で識別可能にする）と REQ-TSK-024（案内を出す）がセットで存在することからの再構成である。
