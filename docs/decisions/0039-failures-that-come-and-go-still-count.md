# 0039. 飛び飛びの失敗も数える

- **状態**: accepted
- **決定日**: 2026-08-29
- **決定者**: 人間
- **反映**: SPEC v2.22（REQ-ERR-004）/ `LogWriteQueue`
- **関連**: [0033](0033-unset-log-path-records-nothing.md) / [0035](0035-a-failure-needs-somewhere-to-arrive.md)

## 文脈

**条文と実装が食い違っていた**（POL-090）。

| | |
| :---- | :---- |
| REQ-ERR-004（`SPEC.md`・**MUST**） | ログファイルへの書き込みに **3回失敗で通知** |
| `LogWriteQueue`（`LogWriter.swift`） | `consecutiveFailures >= 3`。**成功するたびに 0 に戻る** |

**失敗が飛び飛びのとき、両者は違う答えを出す。**

```
失敗 → 成功 → 失敗 → 成功 → 失敗
条文:  3回失敗した → 通知する
実装:  連続は1回 → 黙る
```

**利用者から見て「ログが書けていないことを知らされるか」が変わる。**

この食い違いは、**工程14a（コメントの英語化）の検証役が、訳を条文と突き合わせて見つけた。**
条文にも実装にも、そう決めた理由は書かれていなかった。

## 判断

**連続3回 __または__ 直近10回のうち3回で失敗したとき、利用者に伝える。**
**数える単位は書き込みの試行**であって、ログの行数ではない。

- **連続3回** — 書き込みが継続的に失敗している。これは既存の条件であり、変えない
- **直近10回のうち3回**（新規） — **間欠的に失敗している。** 連続していなくても、
  3割が失敗している状態は正常ではない

いずれかを満たしたら通知する。**通知は一度だけで、成功が続けば再び通知できる状態に戻る。**

**ただし「再び通知できるまで」の長さは変わる**（当初この節は「（既存の挙動）」と書いていたが、**不正確だった**。
検証役が実測して指摘。2026-08-29）。旧実装は**成功1回**で再武装した。新実装は**窓が空くまで**戻らない ——
`F,S,F,S,F` で通知したあとは、**成功6回**を要する。**利用者から見て「2度目の通知がいつ出せるようになるか」が変わる。**

## 理由・設計意図

**「連続」だけを数えると、予測できていない不具合が隠れる。**

連続を要求する側にも理はある —— 一時的に失敗して自力で回復するものを毎回知らせても、利用者にできることはない。
**しかしそれは「失敗の原因を我々が理解している」という前提に立っている。**

**理解していない原因で飛び飛びに失敗している場合、それはまさに知らせるべき状態である。**
連続を要求すると、**そういう不具合ほど静かになる** —— 3回に1回だけ失敗するバグは、
永遠に閾値へ届かない。

**この判断は人間が下した**（2026-08-29）。原文の理由:

> **もしも予測できていなかったバグを抱えていた場合に、飛び飛びの失敗が大問題になるからです。**

**窓を10件、閾値を3件としたのは、既存の閾値（3）を動かさずに済むためである。**
連続3回は「直近10件のうち3件」の特別な場合であり、**新しい条件は既存の条件を包含する。**
実装上は両方を評価するが、条文としては**「連続3回」が独立した意味を持たない**ことに注意する。

### 窓は「回数」であって時間ではない

**この判断には、書いた時点で見落としていた限界がある**（実装役が指摘。2026-08-29）。

**窓は `flush` の回数で数える。時間ではない。** 一日に1回しかセッションを終えない使い方では、
**10件の窓が実時間として10日ぶんに伸びる。**

上の「何ヶ月も前の失敗が閾値に効く」という理由で累積案を却下したが、
**低頻度の利用では、この案も同じことを緩やかに起こす。**

**それでもこの案を採る。** 時間窓を足すと、**閾値3を動かさずに済む最小の窓**という設計の理由が崩れ、
「何分」を決める根拠が新たに要る。**低頻度の利用で窓が伸びること自体は、害が小さい** ——
その利用者にとって、10回ぶんの失敗はやはり10回ぶんの失敗である。

**書いておくのは、この限界が判断の外にあったからである。** 時間窓が必要になったときは、
ここを読んで新しいレコードを起こすこと。

**採らなかった案**

| 案 | 採らない理由 |
| :---- | :---- |
| 条文を実装に合わせる（「連続3回」と書く） | **飛び飛びの失敗を永遠に見逃す。** 上記のとおり |
| 実装を条文に合わせる（成功でリセットしない） | **累積で数えると、何ヶ月も前の失敗が閾値に効く。** 現在の状態を表さない |

## 出典と確度

- **事実**: 条文と実装の食い違いは `SPEC.md` の REQ-ERR-004 と
  `Packages/MdoroCore/Sources/MdoroCore/Log/LogWriter.swift:200,206` を突き合わせて確認（2026-08-29）。
- **判断**: 「飛び飛びの失敗も知らせる」は**人間の決定**であり、推測ではない。
