# 0009. Live Activity の MUST 要件を SHOULD へ降格する

- **状態**: accepted
- **日付**: 2026-08-25

## 文脈

v2.3 では Live Activity の開始（REQ-UIX-020）と更新（REQ-UIX-022）を **MUST** としていた。
[0005](0005-focus-view-instead-of-standby.md) で Live Activity を2系統の片方に据えた時点では、
ロック中も残り時間が追随することを前提に置いていた。

Apple の一次情報で確認した結果、これは**完全ローカル構成では成立しない**ことが判明した。

- Live Activity は**アプリがフォアグラウンドにある間しか開始できない**（例外は APNs による push-to-start のみ）。
- **更新もアプリが running である間しか行えない。** iOS はバックグラウンド移行後まもなくアプリを suspend し、
  その時点で WebSocket も切断される。

APNs は「完全ローカル駆動」（仕様書 第14章）により採用できない。

## 判断

- **REQ-UIX-020 / 022 を MUST から SHOULD へ降格する。**
- 開始できなかった場合は、次にアプリがフォアグラウンドへ復帰した時点で開始する。
- 更新できない状況は `ActivityContent.staleDate`（既定で更新時刻＋90秒）で表現し、
  `context.isStale` が真のとき「情報が古い可能性があります」を明示する（REQ-UIX-023 は MUST のまま）。
- **Live Activity を「セッション終了を知らせる手段」にしない。** 終了の通知は
  絶対時刻のローカル通知（第5章）が担い、Live Activity はアプリが動いている間の可視化に徹する。

## 理由・設計意図

**満たせない要件を MUST に置くと、リリース可否の判断基準が機能しなくなる。**
MUST が1つでも「実際には満たせないが黙認されている」状態になると、他の MUST の重みも失われる。

通知と Live Activity を独立させたのは、**Live Activity が更新できない状況でも通知は必ず届く**ようにするため。
両者を結合すると、片方の制約がもう片方の信頼性を巻き込む。

`isStale` で陳腐化を示すのは、**古い情報を正しい情報のように見せない**ため。
Live Activity 上の一時停止ボタン（REQ-UIX-024）も同様で、Mac への接続に失敗した場合は
状態を変更したかのように見せず `isStale` 表示へ切り替える。

## 影響

- 要件: REQ-UIX-020（MUST→SHOULD）、REQ-UIX-022（MUST→SHOULD）、REQ-UIX-023（MUST 据え置き）、
  REQ-UIX-029、仕様書 8.3 冒頭のプラットフォーム制約
- コード: `PomodoroMac/PomodoroWidget/`（未実装）
- **この判断を覆さないこと。** ここを MUST に戻す提案は、APNs の採用（第14章違反）とセットでなければ成立しない。
  将来 push-to-start を導入する場合は仕様書 第15章 FUT-013
- 関連する未決事項: OPEN-004（無制限モード実装時の Live Activity 再開方法）

## 出典と確度

- **事実**: 仕様書 8.3 冒頭の「プラットフォーム制約（Apple 公式で確認済み）」と
  末尾の「背景・理由（MUST → SHOULD への格下げ）」に条文として存在する。
  制約の内容は Apple の一次情報で確認済みと記録されている。
- **推測**: 「MUST が1つ形骸化すると他の MUST の重みも失われる」という敷衍は、
  条文の「リリース可否の判断基準が機能しなくなる」を展開した再構成である。
