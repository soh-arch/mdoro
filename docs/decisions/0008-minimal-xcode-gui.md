# 0008. Xcode の GUI 操作は他のツールにできないことだけに使う

- **状態**: accepted
- **日付**: 2026-08-24

## 文脈

プロダクトオーナーにとって Swift 開発は初めてであり、Xcode の GUI 操作を学習コストとして抱え込みたくない。
一方 Claude（当時の PM）は、一般的な「Xcode で開発する」前提の手順書を書こうとしていた。

## 判断

- コーディングは主に Claude Code、コードを自分で読むときは Cursor で行う。
- **Xcode は他のエディタにできない役割にのみ使う。** 具体的には
  ターゲット追加・capability 追加・実機デバッグ・Instruments・アイコン作成。それ以外では開かない。
- **`.xcodeproj` を直接編集しない。**

この方針を満たすため、次の3つを構成の前提に置く。

- **Buildable folder**（Xcode 16 以降の既定）: `.swift` をディスクに置くだけでビルド対象に入る
- **ローカル Swift Package**（`Packages/MdoroCore`）: 初回リンクだけ GUI、以降は `Package.swift` のテキスト編集で完結
- **Xcode 26.3 以降の MCP サーバー**（`xcrun mcpbridge`）: ビルド・テスト・SwiftUI プレビュー取得が CLI 側から可能

## 理由・設計意図

エディタとターミナルで完結する部分は、そちらで完結させたい。GUI 手順は再現性が低く、記録も自動化もしにくい。

**制約を先に宣言したことが、結果的により良い構成を引き出した。**
「Xcode をなるべく開かない」という制約を掲げなければ、Buildable folder / ローカルパッケージ / MCP サーバーの
3点を調べに行くことはなく、一般的な GUI 前提の手順書ができていた。とくに MCP サーバーの存在は、
方針がなければ調査対象にすらならなかった。

## 影響

- 構成: `Packages/MdoroCore` を共有コードの主戦場とする。3ターゲットはすべて buildable folder
- `Info.plist` は3ターゲットとも実ファイルとして存在し、XML として直接編集してよい
- 手順: ビルド・テストコマンドと環境メモは `docs/DEVELOPMENT.md`
- 参照: Xcode セットアップ手順書の URL は `docs/CONTEXT.md`
- **AI への適用指針**: 「ディスクにファイルを置けばビルド対象に入る」ため、
  ファイル追加のために `.xcodeproj` を編集しない。GUI 操作を伴う手順を提案する前に CLI で完結する方法を探す
