# 0040. 同一性は名前が担わない。そして使わない機能は立てない

## 文脈

**軸 E と軸 K の監査で、通信まわりに9件が積み上がった。** 個別に直そうとすると、
**どれも同じ3箇所（TXT・Keychain の鍵・Mac の保存形式）に触る**ことが分かった。

### 根にあったもの

**(a) 「この Mac」を指す値が、電波に乗っていない。**

名前が3つあり、どれも同一性を担えない。

| # | 何の名前 | 誰が変えるか |
| :-- | :---- | :---- |
| 1 | Bonjour のインスタンス名 | **mDNSResponder が衝突時に `(2)` を付ける**（[platform/0008](../platform/0008-what-three-tests-rest-on.md) で実測） |
| 2 | `welcome` の `serverName`（＝ `Host.current().localizedName`） | 利用者。**2台が同名になりうる** |
| 3 | `hello` の `deviceName` | 利用者 |

TXT にあるのは `ws` と `v` だけ。**一意な値がない。**
そして **iPhone は Keychain を「Bonjour 名」で引いている** —— **OS が書き換える名前が、鍵になっている**（POL-113）。

**(b) Mac は、発行したトークンが誰のものか覚えていない。**

```swift
public struct DeviceToken { let value: String; let deviceName: String; let issuedAt: Date }
enum DeviceTokenStore { static func save(_ tokens: Set<String>, ...) }   // ← 値だけ保存する
```

**`deviceName` と `issuedAt` は、保存の瞬間に捨てられている。**
**失効 UI が作れないのは、これが理由である** —— 画面に出すものが残っていない。
**「失効経路が無い」より正確には、「失効させる対象を識別できる情報を、自分で捨てている」**（POL-123）。

**(c) 使わない人が、使わない機能の代償を先に払っている。**

サーバーと Bonjour 広告は**起動時に無条件で立つ。** iPhone を使わない利用者は:

- 起動直後に**ローカルネットワークの許可ダイアログ**を見る（**一生使わない機能のために**）
- **Mac の名前が LAN に出る**（見返りゼロ・POL-125）
- リスナー2本と Bonjour 登録を抱える

### 前提として置かれたこと

**人間の言葉**（2026-08-30）:

> **このアプリはただのタスク管理ポモドーロタイマーです。iPhone を併用しない使い方も受け入れる方針です。**
> **利用者に重い負担を求める設計にはしたくない。**

**この一文が設計を決めた。** 「iPhone を使わない使い方を受け入れる」なら、
**その人たちに何も払わせないことが、設計の要件になる。**

## 判断

**5つを一度に決める。個別に直さない。**

### 1. 同一性は `id` が持つ。名前は表示のためだけになる

- **Mac は自分の `id`（UUID）を持つ。** 一度作ったら変わらない
- **TXT に `id` を足す** —— `ws` / `v` / **`id`**。**新しいメッセージは増えない**
- **iPhone は Keychain を `id` で引く。** 表示は名前のまま
- **名前を1つに統合する** —— Bonjour 名・`welcome.serverName`・`/info`・**Live Activity** が、
  すべて**同じ「表示名」**になる
- **表示名は設定できる。既定は `Mdoro`**

### 2. サーバーは、ペアリングが在るときだけ立てる

| 状態 | 振る舞い |
| :---- | :---- |
| 一度もペアリングしていない | **サーバーを立てない。広告しない。許可も求めない** |
| ペアリング画面を開いた | **そこで初めて立てて広告し、コードを出す** |
| ペアリング済み | 起動時に自動で立てる |
| **最後のペアリングを削除した** | **止める** |
| **ペアリング画面を閉じた**（ペアリング済みでなければ） | **止める** |

### 3. 接続状態の表示は、ペアリングが在るときにだけ在る

**一度もペアリングしていない Mac が「未接続」なのは正常な状態である。**
**正常な状態を、不具合に見える形で示さない**（REQ-UIX-046 と同じ理屈）。

**設定で消せるようにはしない。** 「見せるべきでなかったもの」について利用者に判断させることになる。
**既定を正しくすれば、設定は要らない。**

**削除したら表示も消える** —— **削除操作に、目に見える結果が伴う。**

### 4. Mac はトークンを「記録」として保存し、Keychain に置く

**値・端末名・発行日時**を保存する（**いま捨てている情報を捨てない**）。
**置き場所は Keychain** —— iPhone 側と揃う（POL-127）。
**iPhone 側には `kSecAttrAccessible = ThisDeviceOnly` を付ける** —— バックアップから復元されない（POL-131）。

**これで失効 UI が作れる。** 設定に「ペアリング済みの iPhone」1行と削除ボタンを置く。

### 5. 付随して決めたこと

| | |
| :---- | :---- |
| **`GET /info` を消す** | **誰も呼んでいない**（iPhone に参照が1つもない）。`isPairingMode` を外せば残りは全部 TXT か接続時に分かる。**無認証の口とリスナーが1本減る** |
| **既存のペアリングは1回やり直す** | **捨てる予定の形式のために移行コードを書かない** |
| **プロトコル版 `v` を上げる** | TXT の意味と鍵の意味が変わる。**REQ-PRT-004 が非互換を拒む仕組みを既に持っており、古い組み合わせが黙って半分動くのを防げる** |
| **2台目を検出したら、名前の変更を勧める一言を出す** | `serviceRegistrationUpdateHandler` で**自分の広告名が `Mdoro (2)` になったこと**を検出する。**同じ LAN に別の Mdoro が居るとき、そのときだけ**出る。**iPhone を持っていない人にも効く** |

## 理由・設計意図

**名前で同一性を表すのをやめる。**

OS が書き換える値を鍵にしている限り、**利用者は「ペアリング済みなのに未ペアリング扱い」に遭い続ける。**
`id` は利用者から見えない。**負担ではなく、負担の原因を取り除くもの**である。

**名前を1つにするのは、混線が実在するバグを生んでいるからである。**
`ClientModel.pairedServerName` は `client.serverName`（welcome 由来）と `servers.first?.name`（Bonjour 由来）を
混ぜて Keychain を引く。`submitPairingCode` も同型。**3つの名前空間が同じ変数名 `serverName` を共有していた。**
**名前が1つになれば、この種の取り違えは書けなくなる。**

**そして統合すると、個人名が Mac から出なくなる** —— LAN・`welcome`・iPhone の保存・**ロック画面の Live Activity**。
**4箇所すべてで。**

**使わない機能を立てないのは、「弁える」の直接の帰結である。**
機能を削るのではなく、**順番を変えるだけ**である。
副次的に、**ローカルネットワークの許可が正しい文脈で求められるようになる**（REQ-PLT-007 が求めていたこと）。

**採らなかった案**

| 案 | 採らない理由 |
| :---- | :---- |
| 個別に直す | POL-113 / 123 / 125 / 127 が**すべて同じ3箇所**に触る。**同じ場所を4回変えることになる** |
| Bonjour 名だけ設定可にし、`welcome` は Mac の名前のまま | **LAN には出さなくなるが、iPhone の中とロック画面には個人名が残る。** 名前空間の混線も半分残る |
| 既定の表示名を Mac の名前にする | 見分けはつくが、**個人名が出たままになる。****出さないことを既定にし、出したい人が選ぶほうが安全** |
| TLS をここに含める | **証明書の信頼をどう作るかは、それ自体が1つの設計。** `id` とは独立（POL-122 で「公開後」と決定済み） |
| 移行コードを書く | **捨てる形式のために書くコード。** 利用者は現時点で1人 |

**認めた代償**

**表示名の既定が `Mdoro` なので、Mac が2台あると一覧で見分けにくい。**
人間の判断（2026-08-30）:

> **複数になった時、自然に仕様を理解して必要であれば名前を変更しようと思ってもらえる。**
> **選ぶ困難さは、利用者が能動的に変更できるのであれば採ってよいレベルのデメリット。**

**`id` があるので誤接続にはならない。** 分からないのは**選ぶときだけ**であり、
**2台目を検出したときの一言**がそこを埋める。

## 影響

| 対象 | 内容 |
| :---- | :---- |
| REQ-COM-002 / 003 | 広告の開始条件・TXT の中身・`GET /info` の削除 |
| REQ-SEC-002 | トークンの保存形式（記録）と置き場所（Keychain）、鍵が `id` |
| REQ-UIX（Live Activity） | `serverName` の意味が「表示名」になる |
| REQ-UIX（接続表示） | **ペアリングが在るときだけ表示する** |
| REQ-PLT-007 | **より素直になる**（許可がフォアグラウンドの、文脈のある場所で求められる） |
| 第16章 用語集 | 「サーバー名」の定義 |
| **新しい要件** | **増えない。** すべて既存条文の書き換え |
| PUNCHLIST | POL-113 / 123 / 125 / 127 / 131 がこの記録に紐づく |

## 出典と確度

- **事実**: 名前の3系統と `DeviceTokenStore` が値だけを保存することは、
  `Messages.swift` / `Pairing.swift` / `DeviceTokenStore.swift` / `ServerInfo.swift` /
  `ClientModel.swift` を読んで確認（2026-08-30）。
- **事実**: mDNSResponder が衝突時に `(2)` を付け、**番号の若さと登録の新旧に関係が無い**ことは
  [platform/0008](../platform/0008-what-three-tests-rest-on.md) の実測。
- **事実**: `GET /info` が iPhone から呼ばれていないことは、`PomodoroiOS` 配下の全走査で確認。
- **判断**: 上記5つは**人間の決定**であり、推測ではない。
- **推測ではないこと**: 「2台目の検出に `serviceRegistrationUpdateHandler` を使う」は
  **API の存在を [platform/0008](../platform/0008-what-three-tests-rest-on.md) で確認済み**だが、
  **実際に発火するかは実装時に確かめる。**
