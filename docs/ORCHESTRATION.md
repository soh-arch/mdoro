# ORCHESTRATION — オーケストレーターの手順書

**`CLAUDE.md` は規律を、このファイルは手順を書く。**
規律は「なぜそうするか」、手順は「毎回何をするか」である。

**この手順書は、オーケストレーターが誰であっても・どれだけ文脈を持っていても同じ結果になるように書く。**
記憶や気づきに依存する工程は、**道具に落とすか、表に落とす。**

**ここに書かれた工程を飛ばしたら、飛ばしたことを報告する**（`CLAUDE.md`「変更の通し方」）。

**仕組みは他のプロジェクトへ持ち出せる。中身は持ち出せない。**
Mdoro 固有なのは、**§2 の床の表・§3 の環境の制約・§4 のテスト件数の数え方・§8 の表の行**である。
残り（委譲の境界・二つの波・指示書の書き方・裏取り・自分の文章の検査・報告の仕方）は、
**何を作っているかに依存しない。**

**持ち出すのは、この体制の変更が止まってからにする。** いま写しを作れば、
`CLAUDE.md` と `AGENTS.md` で繰り返した「二重に持った事実の片方が腐る」失敗をもう一度やる。
**規律は、それが生まれた事故の隣にあるときだけ効く。** 事故を剥がすと一般論になり、急ぐときに緩む。

## 2. 軸を決める — 二つの波

**床は常に、天井は必要なときだけ。二つは直列にしない。**
床の軸で1本目を投げ、**同時に**軸出しを走らせる。増えた軸があれば2本目を並列で投げる。

### 床（機械的に引く。判断を含まない）

**`python3 Tools/axes-for.py <base>` が下の表を読んで引く。**
表がこのファイルにあり、道具はそれを読むだけなので、**二重に持たない。**
**道具が引けない行は「自分で判断する」として出る。** 落ちない。
**どの行にも当たらなかったファイルも、同じように名前で出る** —— 誰も見ないファイルは、消えた行と同じだけ軸の欠落である。
**先頭に `/` を付けたパターンは、直下のそのファイルだけに当たる**（`README.md` と書くと、`docs/decisions/README.md` にも当たってしまう）。

**軸は「確認する」ではなく「作って、問う」の形で書く。**
「〜が正しいか」は **yes と答えるのが簡単すぎる**。だから、**まず一覧・表・不変条件を作らせ、
それに対して「〜でありうるか」を問う**形にする。**役には、作った一覧そのものを報告に貼らせる。**
貼らせるのは証拠のためだけではない —— **渡した軸を使わず自分の流儀に戻った**ことが、
これでしか見えないからである。
（根拠と反証は `docs/review-axes.md`）

**行を足したら、並び順を決め直す。** 足すだけで順序を見ないのが、この種の表が劣化する主因である。
**最も重要な行を先頭に置く。**触った場所の並びと衝突したら、重要度が勝つ。

**ただし、事故を待たない行もある** —— 上の4つの形（送らない・送ってはならないときに送る・順序・持続）は、
**まだ起きていない事故にも当たる**。**事故駆動だけで育てると、踏んでいない筋には軸が立たない。**

**先頭の行は、他の行とわざと重なる。** `TimerEngine.swift` を触れば**3行**が出る
（この行・`Packages/MdoroCore/`・`AppModel.swift` の行）。
**重複を消さない。** 効率の側は重複を損失として測るが、**壊れたときに利用者の資産が失われる場所では、
この分野は一貫して重複を選んでいる**（`docs/review-axes.md`）。

## 3. 役に出す

- [ ] **指示書に自分の自己評価と結論を書かない。** 渡すのは**成果物・軸・環境の制約**。
      「何を直したか」「なぜそうしたか」を渡すと**指摘が減る**
- [ ] **「新しく見つける」依頼と「直ったか確かめる」依頼を分ける。**
      前回の指摘を並べると追認バイアスが働き、新規の発見が落ちる
- [ ] **環境の制約を毎回入れる**（下の定型）
- [ ] **実出力を報告に貼らせる項目を入れる**（`git log --oneline` / `git diff --stat` / `git status --short`）
- [ ] **提案・懸念・新たな選択肢は採用されていない前提で書く**、を入れる
- [ ] **シェルを渡す役なら、使い捨ての checkout で走らせる**（下の「役に渡す作業ツリー」）

### 環境の制約（そのまま貼る）

- **利用者がこの Mac で Mdoro を実際に使用中である。アプリを起動しない**
- **LAN に触れない**（変異実行で Bonjour の広告が 30ms 漏れた事故がある）
- **本物の Keychain / UserDefaults を汚さない**（注入の継ぎ目を使う）
- **`xcodebuild` には必ず `-destination` を付ける。** 省くと `Debug-iphoneos` としてビルドされ、
  **接続中の実機へ降りる**（2026-09-03 に発生）
- ビルドは `-derivedDataPath /tmp/mdoro-fix`。`swift test` は `Packages/MdoroCore` で走らせる
- **commit・push・PR は禁止**（役による）。作業ツリーを整えたら**申告する**
  —— **申告は `Tools/run-in-a-worktree.py` が機械的にも取る。役の記憶に頼らない**
- シミュレータの `Application failed preflight checks` はテストの失敗ではない。
  `xcrun simctl shutdown all` の後に再実行する

### 役に渡す作業ツリー

**外部プロセスとして起動する役には、使い捨ての checkout を渡す。**

```
python3 Tools/run-in-a-worktree.py -- <役を起動するコマンド>
```

`git worktree` で HEAD の checkout を作り、その中でコマンドを走らせ、終わったあとに
**「どの追跡ファイルが動いたか」を、その checkout と このリポジトリの両方について言う。**
動いていれば checkout を残し、終了コード **3** を返す。

**これはサンドボックスではない。** 絶対パスへ書くコマンドは止まらない。
**止める道具ではなく、黙って書けなくする道具である** ——
`CLAUDE.md` が禁じているのは書き込みではなく、**申告のない書き込み**である。

**作業ツリーが汚れていると走らない。** checkout は commit から作るので、
**未 commit の変更は役に見えない** —— 手元と違うものを検証させないための拒否である
（`--allow-dirty` で越えられる）。

**未追跡のまま残ったもの**（ビルド成果物・下書き）は**「変更」として数えない。** checkout ごと消える。

**終了コード 0 を「指摘が無かった」と読まない。** 何を見つけたかは報告の中にしかない。

**⚠ ハーネスの中で動くサブエージェントは、これで包めない。**
`.claude/agents/` の役は**シェルコマンドとして起動されない**ので、この道具の外側に置けない。
**あちらに効くのは `tools:` による道具の制限だけ**であり、**それでも `Bash` を残す以上、書き込みは止まらない**
（`.claude/agents/reviewer.md`）。

**2026-09-09、この節を書いた当人が、その直後の検証で守れなかった** ——
**守り忘れではなく、包めない役だったからである。**
検証役が `git worktree list` を実行して1行しか返らないことを報告し、そこで分かった。
**この節の最初の稿は「シェルを持つ役には」と書いており、射程を言い過ぎていた。**

### 並列にしてよいもの

**読むだけの検証は並列でよい。** **道具を使う検証は同時に1体だけ。**
ビルド資源（DerivedData・シミュレータ・実機）は単一で、2体が同時にビルドすれば踏み合う。

## 7. 人間に報告するとき

**認知負荷を減らすのはこの体制の目的であり**、この節はそれを報告の場面で具体にする。**もう1つの目的は、一つずつ片付けて意思決定を速くすることである。**

- **何を判断してほしいのか**を最初に書く。判断が要らないなら、そう書く
- **オーケストレーターが判断を求めるときは、一度に1つだけ求める。** 複数並べると、
  どれから答えても残りが宙に浮く。**一つずつ片付けるほうが速い**
- **記号を平易な言葉に置き換える。置き換えられないなら、記号に意味を併記する。**
  「`1e309`」ではなく「**1のあとに0が309個並ぶような、大きすぎる数**」。
  ファイル名・要件ID・コミットの識別子も同じで、**それが何を指すのかを一緒に書く**
- **背景・何が問題か・選択肢**を示してから判断を求める。
  選択肢には**それぞれ何を得て何を失うか**を書く
- **事態の優先度に応じて説明の量を調整する。** 後戻りの利かないもの・費用のかかるもの・
  条文や体制を変えるものには、背景と選択肢を尽くす。
  **戻せるもの、軽いもの、報告するだけのものに、長い前置きを付けない**
- **飛ばした工程・確かめられなかったこと**を書く
- **短さは目的ではない。目的は読む側の負担を減らすことである。**
  記号で短くしても、読み手が意味を復元する手間が増えれば差し引きで損をする。詳細は求められたら出す

**2026-09-07 に書き直した。** それまでは「長さは短いほうがよい」とだけ書いてあり、
**記号を使うことは止めていなかった。** オーケストレーターが**大きすぎる数を `1e309` とだけ書き**、
利用者が**記号ではなく意味で説明せよと言い直した。****短くしたのに、往復は増えた。**
（この経緯はリポジトリには残っていない。**この節自身が唯一の記録である。**）

## 8. どこで走るか

**線は「どこに置いてあるか」ではなく「何を要するか」で引く。**
`Packages/MdoroCore` かどうかはパッケージングの都合であって、検査に何が必要かとは関係がない。

**CI が守るのは、このリポジトリが「一度壊れた」と記録している場所である**（人間の言葉・2026-09-12）。
そういう場所ほど、置いてある都合で守られていないことがある。

**オーケストレーターはクラウドで走れる。** ローカルに縛られているのは、**機械か人間を要する工程だけ**である。
**PC のスリープで作業が止まるほうが、往復が増えるより高くつく。**

| 工程 | どこで | 何を要するか |
| :---- | :---- | :---- |
| 条文・Decision Record・この手順書・`docs/PUNCHLIST.md` の編集 | クラウドでよい | `git` と `python3` |
| 読み取りの監査（`spec-auditor` / `repo-auditor`） | クラウドでよい | 読むだけ |
| 軸出し（天井） | クラウドでよい | 渡すのは差分だけ |
| 実装（`MdoroCore`） | **クラウドでよい** | **書くのはクラウド、テストは CI**（`macos-latest` で `swift test`）。手元では走らない |
| **Mac アプリ側の単体テスト**（`MdoroMacTests`） | **CI が見る**（2026-09-12 から） | **何も要さない。**配線の検査であり、実機も LAN も人間も要らない。`xcodebuild` はランナーにある |
| iOS 側のテスト（ターゲット `MdoroiOSTests`・フォルダ `PomodoroiOSTests/`） | **ローカル** | **シミュレータ。**`-only-testing:` に書くのは**ターゲット名**である —— フォルダ名を書くと1本も走らずに緑になる |
| ~~UI テスト~~ | — | **存在しない。**`MdoroMac.xcscheme` / `MdoroiOS.xcscheme` が `PomodoroMacUITests` / `PomodoroiOSUITests` を参照しているが、**`project.pbxproj` にその名前は1度も出てこない**（2026-09-14 に実測）。**scheme に残った切れた参照である**（POL-248） |
| **変異テスト** | **ローカル** | **手作業。**1行壊して走らせる工程で、道具が無い |
| ビルドの確認・実機での確認 | **ローカル** | `xcodebuild`・シミュレータ・実機・DerivedData は**単一**で、この Mac にしかない |
| capability・署名・ターゲットへのリンク | **人間** | Xcode の操作（[0013](decisions/0013-pbxproj-is-owned-by-xcode.md)） |

**ローカルに残る理由は4つしかない** —— **手作業である**（変異テスト）／**機械が要る**（シミュレータ・実機）／
**人間が要る**（Xcode の操作）／**利用者がその Mac で Mdoro を使用中である**（アプリを起動しない・LAN に触れない）。
**この4つに当たらない検査がローカルに残っていたら、それは置き場所の都合である。**

**測った（2026-09-12・POL-225）**: `MdoroMacTests` は**ランナーで走る。当時48本・ジョブ全体で72〜81秒・署名は切って足りる**（**2026-09-14 に4本足したので52本になったが、その本数での実測はまだ無い** —— Actions の分が尽きたため。POL-239 / POL-237）
（`CODE_SIGNING_ALLOWED=NO`。Keychain も通知も注入した継ぎ目を通るため）。
**アプリはホストとして起動する。**本物の署名を要するテストがあれば、**それは「この検査はこの Mac のものだ」と言っている。**

**この線が曖昧だと、時間で払う。** POL-189 は**9日止まった** —— 「この件は Mac でしか動かない」が3箇所に書かれていたが、
**CI はその間ずっと `swift test` を走らせていた。「Mac が要るもの」と「Mac に置いてあるもの」を同じ言葉で語っていたので、誰も正しく思い出せなかった。**

### CI は無料ではない

**macOS のランナーは Linux の10倍で課金され、ジョブごとに分単位で切り上げられる。**
`mac` ジョブを足したとき、オーケストレーターは利用者に「**72秒**」と説明した。**分では約20分だった。**
**時間で答えて課金で答えなかったのは誤りである**（POL-239。2026-09-12、口座が月の90%に達して分かった）。

**走らせる前に、分で見積もる。**秒ではなく。

| いま | 実測（2026-09-12） |
| :---- | :---- |
| コードを触る PR | **25分**（Linux の門1分 ＋ macOS 2分×10 ＋ `tools` 4分） |
| 文書だけの PR | **5分**（macOS へ進まない） |

**削減前は34分だった。**（**この表は一度「約14分」と書いて間違えた** —— `1 + 20 + 4` は 25 である。
**単位を直した同じ文で足し算を落とした。**数は、単位を直したあとにもう一度足す。）

**そのうえで、次の2つを方針とする**（人間・2026-09-12）。

1. **料金がかかるくらいなら、Claude でできることは Claude でやる。**
   **読んで数えれば分かることに、macOS の20分を使わない。**
   2026-09-12、変異テストが走らせられない環境で「1行ごとに、壊したらどのテストが落ちるか」を読んで答えさせ、
   **噛まない箇所を11見つけた**（POL-234）。**走らせずに出た。**
2. **1つの PR を merge するまでの、作業全体の時間を見る。**
   **CI の往復1回は、待ち時間と課金の両方を使う。**赤い CI を「もう一度押して様子を見る」で消費しない ——
   **押す前に、次の1回で何が分かるかを決める。**
   2026-09-12、実装役は落ちた4本の所要時間だけから**「リスナーは上がっている」「クライアントが `.ready` に届いていない」**を算術で確定させ、
   **残る候補を1回の実行で二分する形**に直した。**3回目を待たない設計である。**

**途中でローカルの資源が要るとわかったら、そこで止めて申告する。** クラウドから届かないものを
「届いたことにする」経路を作らない。

### クラウドからシェルを触るとき

**実行役（軽量なモデル）に渡し、判断させない。** 渡すのはコマンドで、頼むのは実行と貼り付けだけである。

- **出力は全文を貼らせる。要約させない。** 要約された時点で、裏取りが「読む」から「信じる」に変わる
- **数を主張に使うなら、何を数えたコマンドも書く。**
  `grep -c` は**行数**、`grep -o | wc -l` は**出現数**で、同じファイルに別の数を返す
- **打ち間違いは実行役では捕まらない。** 実行役は言われたとおりに実行するので、
  **間違ったコマンドの正しい出力**が返る。読むのはオーケストレーターの仕事である

### 承知のうえで失うもの

- **ビルドとテストの最後の一歩が、貼られた出力への信用になる。自分で叩き直せない**
- 1コマンドあたり1往復増える。**トークンは増え、速度は落ちる**
