# 検証役の基盤モデルを比べるための資料

**目的**: 検証役（`.claude/agents/reviewer.md`）に Anthropic 以外のモデルを使うことを検討するにあたり、
**候補を同じ土俵で比べるための材料を1箇所に置く。**

このファイルは**単体で読めるように書く。** 会話の記憶を前提にしない。
教材の原文は git から取れるので、**必ず実物を渡すこと**（このファイルの引用は要約ではなく逐語だが、
渡すときは `git show` の出力を使う）。

---

## 1. 検証役とは何をする役か

`.claude/agents/reviewer.md` が正本。要点だけ再掲する。

- **独立コンテキストで成果物だけを見る。** 実装時のやりとりは渡さない
- **直さない。** 指摘を列挙する。commit・push・PR をしない
- 指摘には **根拠**（要件ID / `docs/CONTEXT.md` の項 / Decision Record 番号）、**場所**（`パス:行`）、
  **破綻する条件**（どんな入力・状態でどう壊れるか。再現できないものは「疑い」と明記）を付ける
- 最後に**実行したコマンドと結果**、**検証できなかった要件とその理由**を必ず書く

**この役が実際に何を見つけたかは §3 の教材が示す。**

## 2. 前提 —— すでに決まっていること

**2026-09-03、`CLAUDE.md`「権限」を書き換えた**（[0041](decisions/0041-a-role-answers-for-its-check.md)）。
**線は「どのモデルが作ったか」ではなく「役に何の権限があるか」で引く。**
外部ベンダーのモデルを検証役に据えること自体は、**条文上すでに許されている。**

決まっているのは次である。**これは候補がどれでも変わらない。**

- **サブエージェントに完了承認の権限はない。「指摘なし」は merge の許可ではない**
- 検証役の出力は**指摘の列挙**であり、**採否はオーケストレーターが理由付きで判断する**（採らないなら理由を1行）
- **検証役は自分の検証に責任を持つのであって、成果物全体の品質に責任を持つわけではない**
- 仕様・設計の最終決定と merge は**人間のみ**

**したがって比較で決めるのは「信頼してよいか」ではなく、「どの軸で何を見つけるか」である。**

### これまで検証役が動いていたモデル

**`.claude/agents/*.md` に `model:` が無く、`settings.json` にも既定の指定が無い。**
つまり**親セッションのモデルを継いでいた**（このリポジトリの作業では Opus 5）。
**対照群を作るには、まず固定する必要がある** —— そうしないと「何と比べたか」が後から言えない。

**2026-09-03 の裁定**: `.claude/agents/reviewer.md` に **`model: sonnet`** を書いて固定する。
**運用したい水準そのものを基準にするため**であり、深い1本が要るときは**呼び出し側でモデルを上書きする**
（役ファイルの指定より呼び出し側が優先される）。**これは既定を下げる変更である。**

## 3. 教材 —— 実際に落ちた稿と、期待される指摘

**教材E を除き、git に実物がある**（E は §9 の手順で再現する）。候補モデルには**条文の全文と、その時点のリポジトリ**を渡すこと。
「この条文の問題を挙げよ」とだけ言い、答えは見せない。

抽出コマンド:

```bash
git show <hash>:docs/SPEC.md | grep '^| \*\*REQ-PRT-005\*\*'
```

### 教材A —— `6308396`（REQ-PRT-005 追記の1稿目）

> **既知のフィールドに載る未知の値は、これに当たらない。** プロトコル版が完全一致しなければ接続は成立しない
> （REQ-PRT-004）ため、**同じ版の中に現れた知らない値は、新しい相手ではなく異常である**
> （版を上げずに値を足した、あるいは壊れている）。REQ-ERR-009 の破損メッセージとして扱い、破棄して数えること。

**期待される指摘（major）**: 根拠が**証明しすぎている。** 「版が一致しなければ繋がらない」は
**未知のメッセージ種別にもそのまま当てはまる**ので、同じ条文の前半（前方互換性＝未知の種別は無視する）が
空文になる。同じ理屈で未知の種別も「数える」ことになり、**将来の Mac が新しい種別を10通送っただけで
古い iPhone が再接続ループに入る。**

**副次**: 「版を上げずに値を足した」は、**どの条文にも Decision Record にも無い前提**である
（「値を足したら版を上げる」という一般則は存在しない）。

### 教材B —— `b79b76c`（2稿目・前半）

Aに「**版の違う2台が唯一やり取りするのは `hello` とその拒否までであり**、そこで未知の値を受け取っても
線はそのまま終わるので、数えることに実害はない」を足したもの。

**期待される指摘（major）**: **「唯一」が誤り。** `MdoroServer.handle` は**認証前にすべての
クライアントメッセージ種別を処理する** —— `timeSyncPing` に応答を返し、`heartbeat` を記録する
（門があるのは `command` と `requestSnapshot` だけ）。**コードを読まないと出ない指摘。**

### 教材C —— `44ee360`（3稿目）

> …**ただし拒否（`authFailed`）を握り潰してはならない** —— 理由の語が読めなくても、**拒否されたこと自体は
> 利用者に示すこと**。REQ-PRT-004 は非互換のとき両端末に更新を促すことを求めており、**拒否は捨てたら
> 次が来ない最後の1通である。**

**期待される指摘（major・複数）**:

1. **この例外条項は不要である。** 10.2 は非互換を **`error.code` の `protocolVersionMismatch`** に
   割り当てており、`authFailed.code` の一覧には無い。**条文どおりならその値は全版のカタログにあるので
   握り潰しは起きない。** 懸念の実体は**実装の逸脱**（`Pairing` が非互換を `authFailed(.unknownDeviceToken)`
   で返している）であって、条文の穴ではない
2. **新しい義務である。** 「拒否されたこと自体を示せ」は `authFailed` **全般**を縛るが、
   REQ-PRT-004 が語るのは非互換の場合だけ。しかも「更新を促す」より**弱い**
3. **争点だった「数える」の理由が空白になった。** 新しい根拠（寄せて読むと偽られる）が支えるのは
   「寄せて読むな」までで、「数える」を支えない

### 教材D —— `b95b38d`（閉じた集合で線を引こうとした稿）

免除の非適用を「**値の集合が閉じているフィールド**（**`type`** / `code` / `action` / `event` など）」に
限定したもの。

**期待される指摘（major）**: **例示に `type` を入れたことで、前半を取り消している。**
未知のメッセージ種別とは `type` に載る未知の値そのものであり、**教材Aと同じ破綻を、原理ではなく例示で
繰り返している。**

**副次（major）**: 同型の衝突が **REQ-CFG-018**（範囲外の設定値に `settingOutOfRange` を返す・MUST）
とも残る。`appearance` / `menuBarDisplayMode` は列挙型なので「閉じた集合」に落ち、
**条文は「破棄せよ」、REQ-CFG-018 は「応答を返せ」と言う。**

### 教材E —— v2.34 の1稿目（**git に無い。working tree のみで破棄された**）

条文の該当箇所に次を足したもの。**再現するには、`443e4f5:docs/SPEC.md` の REQ-PRT-005 から
「破棄したメッセージを理由に…」の文を削り、代わりに以下を置く。**

> **1通の未知の値で接続を切ってはならない。破棄するのはそのメッセージだけであり、線は保つこと。**
> （この保証を REQ-ERR-009 だけに預けると、あちらは SHOULD であるため、**条文を守ったまま1通で切る
> 実装が成り立つ** —— 前方互換がいちばん防ぎたい結末である。）

**期待される指摘（major）**: **穴が塞がっていない。** この MUST が縛るのは **n=1 だけ**で、
**2通目で切る実装は条文を完全に守る。** しかも将来この版に無い列挙値が1つ足されると、
その値は `stateSnapshot` に毎回載るので**2通目は数秒で届く。** 防ぎたかった結末はそのまま起きる。

**副次**: 括弧書きの理由（「1通で切る実装が成り立つ」）は、**そのまま「2通で切る実装も成り立つ」に通る。**
理由が要求より広い射程を求めている。

**副次**: 上位概念（「未知の値」）を持ち出したため、`hello` の非互換な版（REQ-PRT-004）や
未登録トークン（REQ-SEC-003）による拒否まで縛るように読め、**MUST どうしで衝突する。**

## 4. 採点の目安

**満点を求めない。** 上の教材は、**実際に Claude の検証役が見つけたもの**である。

| 段 | 内容 |
| :---- | :---- |
| **必須** | 教材A・D の「前半を空文にする」を見つけられること。**条文を読むだけで出る指摘であり、これを落とすモデルは条文の軸に使えない** |
| **望ましい** | 教材E の「n=1 しか縛らない」。**射程の数え方に踏み込む必要がある** |
| **上位** | 教材B・C。**リポジトリを読まないと出ない**（`MdoroServer.handle` の門の有無、10.2 のカタログの割り当て） |
| **減点** | 存在しない条文・要件IDを根拠に挙げる。再現していない指摘を断定で書く。**「問題なし」で終える** |

**偽陽性の扱い**: 指摘が誤っていること自体は減点しない —— Claude の検証役も1度、
外側で包まれた例外の型を見て誤った指摘を出した（`docs/platform/0012`）。
**減点するのは、根拠を示さずに断定すること**である。誤っていても根拠が書いてあれば、実測で覆せる。

## 5. 道具の有無で何が変わるか

**このリポジトリで価値の高かった指摘の多くは、読むだけでは出ない。**

- **変異テスト**: 観測点を替えた実装が、実は**文順に依存していて脆い**ことは、
  「振る舞いの変わらない整理」を実際に当てて初めて分かった
- **スイートの実行**: `xcodebuild` のログは**行が食い込み、行頭が丸ごと消える**ことがある。
  件数を数えるだけだと**実体のない減少**を拾う（`' passed on '` の出現数で数える）
- **コードの追跡**: 「応答が返っていない」「認証前に応答する」は、経路を辿らないと出ない

**読むだけのモデルを使うなら、置き換えではなく「条文の軸」を足す形にする。**
コードの検証役は、シェルとテストを実行できる形を残す。

## 6. 運用の形 —— 選定と本番は別である

**7体は選定の数であって、運用の数ではない。**

### 選定（1回だけ）

- **7モデル × 教材5本を、同じ入力・同じ渡し方で1回。** 道具は渡さない（下の「道具の渡し方」の段階1）
- **合議しない。多数決は主張の数であって、正しさではない。** 出た指摘は個別に採否を判断する
- 測るのは4つ: **必須段を通るか / 根拠を書くか / 断定と疑いを区別するか / 費用**

### 本番

- **常用は2〜3体。** 同じ軸に同じ視点を足しても得るものは少ない。**視点の違うほうを選ぶ**
- **第一候補は「天井」（軸出し）に別ベンダーを混ぜること**（`docs/ORCHESTRATION.md` §2）。
  軸出しは**出力が短く、正解が一意でなく、視点の差がそのまま出る。** 費用も小さい
- **床の軸は道具が要る**（§5）。読むだけのモデルは**置き換えではなく追加**にする

### 道具の渡し方は段階を踏む

1. **道具なし**（差分と条文だけ）—— **選定はここでよい**
2. **読み取りのみ**（`git show` / `grep`）
3. **テスト実行**（`swift test` / `xcodebuild`）—— ここから**機構側の担保**が要る。
   `-destination` を強制するラッパー、書き込み権限の制限。
   **指示書に書いてあっても実機事故は起きた**（§7 の環境の制約）

## 7. 候補に必ず渡すもの

- `CLAUDE.md` / `.claude/agents/reviewer.md` / `docs/CONTEXT.md`（§2「実装で壊しやすい6箇所」を含む）
- 対象の差分と、その時点のリポジトリ
- **環境の制約**（下記）

### 環境の制約（そのまま渡す）

- **利用者がこの Mac で Mdoro を実際に使用中である。アプリを起動しない**
- **LAN に触れない。** 過去に変異実行で Bonjour の広告が 30ms 漏れた
- **本物の Keychain / UserDefaults を汚さない**（注入の継ぎ目を使う）
- **`xcodebuild` には必ず `-destination` を付ける。** 省くと `Debug-iphoneos` としてビルドされ、
  **接続中の実機にアプリが降りる**（2026-09-03 に発生）
- ビルドは `-derivedDataPath /tmp/mdoro-fix`。`swift test` は `Packages/MdoroCore` で走らせる
- **commit・push・PR は禁止。** 作業ツリーを整えたら**必ず申告する**

**指示書の文言だけに頼らないこと。** 上の実機事故は、指示書に書いてあっても起きた。
外部モデルにシェルを渡すなら、**書き込み権限を落とす・ラッパーで `-destination` を強制する**などの
**機構側の担保**を検討する。

Claude の検証役 1回あたり: **6〜15分**、**10万〜15万トークン規模**（対象の大きさによる）。
