# 0009 — 実機で確かめた2つの振る舞い（2026-09-02）

**問い**: (a) `NWListener.serviceRegistrationUpdateHandler` は、mDNSResponder が衝突で
サービス名を書き換えたとき、実際に呼ばれるのか。
(b) ローカルネットワーク許可を OFF にすると、既に立っている登録・接続はどうなるのか。

**方法**: 所有者による実機テスト（このリポジトリの Mdoro を実際の Mac / iPhone で運用中の環境）。
計測コードではなく目視。**確度は「実測」だが、1機・1回の観察である。**

**対象**: macOS 26 / iOS 26（所有者の機体。2026-09-02）

## (a) serviceRegistrationUpdateHandler は呼ばれる

2つ目の Mdoro インスタンスを起動して名前を衝突させたところ、
**設定 > Connection の改名案内（handler の発火だけが表示条件）が表示された。**

- 実装（PR #39）は handler が呼ばれなくても壊れない設計にしてあったが、**呼ばれる側も実証された**
- Decision 0040 判断5 の成立条件が、これで全て実機確認済みになった

## (b) 許可 OFF は、既に立っているものには効かない。効く場面では黙って効く

| 操作 | 観察 |
| :---- | :---- |
| 接続中に許可 OFF | **何も起きない。**表示・タイマー操作・接続すべて従来どおり。iPhone アプリのタスクキル→再起動でも変化なし |
| 許可 OFF のまま Mac アプリを再起動 | **iPhone から見えなくなる**（Not connected）。**Mac にはエラーが1文字も出ない** |

- 拒否は**既存の登録・接続には即座に効かず**、新しい登録に効くと観察と整合する
- Mac 側の**新規の広告が拒否されたとき、アプリはそれを検出できていない** —— リスナーの bind は
  LAN 許可と無関係に成功するため、既存の失敗経路（bind 失敗）を通らない。
  **これはアプリの欠陥として POL-164 に起票した**（振る舞い自体はプラットフォームの事実）

## 確かめられなかったこと

- handler が呼ばれる**タイミングと回数**（登録直後か・遅延があるか・インターフェイスごとに複数回か）
- 許可 OFF が既存登録に効かないのが**仕様か・タイミングの問題か**（長時間 OFF のまま維持した場合は未観察）
- iOS 側の同じ切り替え（iPhone の許可 OFF → 既存接続）は個別には観察していない
