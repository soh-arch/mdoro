## 0. 本書について

### 0.1 要求レベルの定義

| レベル | 意味 |
| :---- | :---- |
| **MUST** | 実装必須。満たさない場合はリリース不可。 |
| **SHOULD** | 推奨。初期リリースに含まれていることが望ましい。合理的な理由があれば見送り可。 |
| **MAY** | 任意。将来的な拡張、または開発リソースに余裕がある場合に実装。 |

## 1. 概要

### 1.1 目的

- **Mac と iPhone の密な連携:** Mac をコア（状態管理の主体）、iPhone を表示・操作端末とする、Apple エコシステムに最適化した集中セッションタイマーを提供する。
- **Markdown ファイルとの安全なデータ連携:** Markdown で書かれたタスクファイル（既定名 `Task.md`）を読み取り専用で利用し、タスクの選択とタイマーを紐付ける。実績ログは別ファイルへ追記のみ行う。**特定のツールを前提としない。** Obsidian / Logseq など、md を素のファイルとして扱う道具であればよい（`decisions/0023`）。
- **集中を妨げない体験:** 接続の安定性と高い視認性を担保し、利用者が過集中（フロー状態）を維持できる環境を目指す。
- **公開を前提とした簡潔さ:** GitHub で OSS として公開する（`decisions/0021`）。対象は **Markdown でタスクを管理する利用者**。広告・課金・計測を持たず、機能を増やすことより挙動が透明であることを優先する。

**背景・理由:** **状態の正本を Mac 1台に固定し**（`decisions/0001-mac-as-single-source-of-truth.md`）、ローカル環境での運用に特化することで、複雑な同期競合を排除し、シンプルで信頼性の高いタスク・時間管理を実現するため。

### 1.2 スコープ

**含むもの**

- Mac 用ネイティブアプリ（SwiftUI / macOS）
- iPhone 用ネイティブアプリ（SwiftUI / iOS）
- 両者を結ぶ LAN 内リアルタイム同期基盤
- Markdown のタスクファイルの読み取りと、実績ログファイルへの追記

**含まないもの（非スコープ）**

- クラウド同期、アカウント機能、1つのインストールで複数人分の設定・実績を切り替える機能
- iPad / Apple Watch / Apple TV 対応（第15章に MAY として記載）
- Obsidian / Logseq などのプラグインとしての実装
- タスクの作成・編集・完了操作（すべて利用者の Markdown エディタ側で行う運用）
- **英語以外の UI 言語**（`decisions/0022`）
- LAN 外（インターネット越し）からの接続

### 1.3 技術前提

| 項目 | 決定内容 |
| :---- | :---- |
| Mac アプリ | SwiftUI（macOS ネイティブ）。メニューバー常駐＋メインウィンドウ。 |
| iPhone アプリ | SwiftUI（iOS ネイティブ）。ActivityKit による Live Activity を含む。 |
| 通信 | WebSocket（JSON）＋ Bonjour（mDNS）による探索。 |
| 最低 OS | **macOS 26 / iOS 26。** 旧 OS を支えると、macOS 15 で導入されたローカルネットワークプライバシーの有無による挙動分岐を抱え込むため。 |
| 通信実装 | Network.framework（REQ-PLT-002）。Apple が Bonjour + WebSocket の推奨構成としている。 |
| 配布 | **ソースからのビルドのみ**（`decisions/0021-published-as-oss-named-mdoro.md`）。利用者は自身の Apple ID でビルド・署名する。無償の Personal Team では7日ごとの再署名が必要であり、Live Activity は widget extension として App ID をもう1つ消費する。 |

**背景・理由:** ローカル通知の事前スケジュール、Live Activity、画面スリープ抑止、メニューバー常駐といった本仕様の中核機能は、いずれもネイティブ実装でなければ実現できないため。

```
│                                                          │
│   [UI / Operation]   [集中表示ビュー]                     │
│   [Live Activity]    [Local Notification Scheduler]      │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 2.1 端末・アプリケーションの役割

**Mac（サーバー・状態の主体）**

- タイマーのロジック実行、状態管理の全権。
- `Task.md` のファイル監視とパース。
- 実績ログファイルへの追記。
- iPhone からの接続を受け付ける通信サーバー機能。
- 設定値の保持と永続化。

**iPhone（クライアント・端末）**

- Mac から受信した状態のリアルタイム反映（表示）。
- 利用者操作（開始/停止/タスク選択など）をコマンドとして Mac へ送信。
- 受信した `sessionEndAt` に基づくローカル通知の事前スケジュール。
- Live Activity の表示・更新。

**Markdown ファイル（外部データ）**

- タスクファイルを提供する。本システムからは一切の書き込みを行わない。
- ログファイルを保管する。本システムは追記のみ行う。
- 置き場所は利用者の管理下にある（Obsidian の保管庫、Logseq のグラフ、ただのフォルダのいずれでもよい）。

**背景・理由:** 状態管理の主体を Mac に一本化することで、複数端末によるデータの先祖返りや競合を根本的に防ぐ。

## 3. 通信・同期仕様

### 3.1 接続アーキテクチャ

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-COM-001** | **MUST** | Mac を親（サーバー）、iPhone を子（クライアント）とするアーキテクチャで実装すること。 |
| **REQ-COM-002** | **MUST** | 状態同期は WebSocket（JSON メッセージ）で行うこと。HTTP は Bonjour 発見後のサーバー情報取得（`GET /info`）にのみ使用し、状態同期には用いないこと。`GET /info` はサーバー名・プロトコルバージョン・ペアリングモードの有無のみを返し、**認証を要さない代わりに状態や設定を一切含めないこと。** |
| **REQ-COM-003** | **MUST** | 利用者が IP アドレスを手動入力しなくて済むよう、mDNS（Bonjour, サービス型 `_mdoro._tcp`）による自動端末検出・接続機能を実装すること。 |
| **REQ-COM-004** | **MUST** | 一時的なネットワーク遮断時は指数バックオフ（初回1秒、上限30秒）で自動再接続を試みること。再接続に成功した場合は、差分ではなく完全な状態スナップショットを受信して状態を上書きすること。 |
| **REQ-COM-005** | **MUST** | サーバー・クライアント双方は5秒間隔でハートビートを送受信し、15秒間応答がない場合は接続断とみなすこと。 |
| **REQ-COM-006** | **SHOULD** | 状態の送信は「状態が変化したとき」のみ行うこと。残り時間の刻みを毎秒送信してはならない（絶対時刻基準のためクライアント側で算出可能）。 |

**背景・理由:** 作業セッション中の「繋がらない」「設定が面倒」といったストレスをゼロにし、作業への中断を最小限にするため。また、毎秒の送信を避けることでバッテリー消費と実装複雑度を抑える。

### 3.2 ペアリングと認証

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-SEC-001** | **MUST** | 初回接続時は、Mac 画面に表示された6桁のペアリングコードを iPhone に入力させること。認証成功時、Mac はデバイストークンを発行し、iPhone はこれを Keychain に保存すること。 |
| **REQ-SEC-002** | **MUST** | 2回目以降の接続は保存されたデバイストークンで自動認証し、利用者操作を不要とすること。 |
| **REQ-SEC-003** | **MUST** | 有効なトークンを持たないクライアントからの接続要求は拒否すること。ペアリングモードは Mac 側で明示的に開始したときのみ、かつ3分間のみ有効とすること。 |
| **REQ-SEC-004** | **MUST** | 既に別のクライアントが接続中の状態で新たな接続要求があった場合、Mac 側に確認を表示し、利用者が承認した場合のみ既存接続を切断して新接続を受け入れること。**確認は 60 秒で自動的にタイムアウトし、既定は拒否（`connectionRejectedByUser`）とすること。** |
| **REQ-SEC-005** | **MUST** | ローカルネットワーク許可（iOS・macOS 双方。3.5 参照）およびファイアウォール受信許可について、未許可を検出した時点で、拒否理由と設定アプリの該当画面への遷移ボタンを含むシートを表示すること。 |
| **REQ-SEC-006** | **MAY** | 自己署名証明書による TLS（`wss://`）に対応する。 |

**背景・理由:** 「Mac 1台対 iPhone 1台」を原則として掲げる以上、LAN 内の任意の端末から接続・操作できてしまう状態ではその原則が担保されないため。

### 3.3 時刻同期

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-COM-007** | **MUST** | 接続確立時およびハートビートごとに、NTP 方式（`t1` 送信、`t2` 受信、`t3` 応答送信、`t4` 応答受信）で端末間の時計オフセットを測定すること。 |
| **REQ-COM-008** | **MUST** | オフセットは `((t2 − t1) + (t3 − t4)) / 2`、往復遅延は `(t4 − t1) − (t3 − t2)` で算出すること。往復遅延が 500ms を超えるサンプルは棄却し、**棄却後の直近 7 サンプルの中央値**を採用すること。有効サンプルが 3 件未満の間は、最小往復遅延のサンプルの値をそのまま用いること。 |
| **REQ-COM-009** | **MUST** | クライアントは受信した `sessionEndAt`（サーバー時刻）に測定オフセットを適用してから残り時間を算出すること。 |
| **REQ-COM-010** | **MUST** | 残り時間の算出には単調増加時計（`ContinuousClock` / `mach_continuous_time`）を用い、壁時計は `sessionEndAt` の生成・ログの時刻表記・論理日の判定にのみ用いること。壁時計が単調時計に対し 2 秒以上乖離した場合は、時刻同期を再実行し通知を再スケジュールすること。 |
| **REQ-COM-014** | **MUST** | ローカル通知のスケジュールに `UNCalendarNotificationTrigger` を用いる場合、`DateComponents.timeZone` を明示的に設定すること。タイムゾーン変更・サマータイム移行によって発火時刻がずれることを防ぐ。 |

**背景・理由:** 絶対時刻同期は本システムの設計の根幹だが、Mac と iPhone の内部時計には数百ミリ秒〜秒単位の差が生じうる。補正なしでは「終了絶対時刻」という基準そのものが端末間でズレる。

### 3.4 切断中の挙動

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-COM-011** | **MUST** | 接続断の状態でも、iPhone は最後に受信した `sessionEndAt` に基づき**表示上のカウントダウンを継続してよい**（表示の補間は許可）。 |
| **REQ-COM-012** | **MUST** | ただし iPhone は、表示が 00:00 に到達してもセッション完了を**確定させてはならない**。同期待ちであることを示し、周回数の加算やログ記録を行ってはならない。セッション完了の判定は常に Mac のみが行う。 |
| **REQ-COM-013** | **MUST** | 接続断中は、iPhone 画面上に接続状態インジケータを常時表示すること。操作系 UI は無効化し、Mac に接続していないことを明示すること。 |

**背景・理由:** v1.0 の「iPhone が勝手に時間を進めてはならない」という制約は、切断中の表示要件と字義上矛盾していた。「表示の補間」と「状態の確定」を分離することで、体験を損なわずに単一の真実を守る。

## 4. タイマー仕様

### 4.1 状態モデル

タイマーの状態は、**セッション種別（SessionType）** と **実行状態（RunState）** の2軸で表現する。

**SessionType**

| 値 | 意味 |
| :---- | :---- |
| `WORK` | 集中作業セッション |
| `SHORT_BREAK` | 短い休憩 |
| `LONG_BREAK` | 長い休憩（一定周回ごと） |

**RunState**

| 値 | 意味 |
| :---- | :---- |
| `IDLE` | セッション未開始。何も走っていない。 |
| `RUNNING` | セッション進行中。 |
| `PAUSED` | 一時停止中。残り時間を保持。 |
| `FINISHED` | 終了時刻に到達し、猶予（1分）の中で延長・中断を待っている状態。ログは未確定。 |
| `PENDING_DECISION` | 復元時に「不在中に終了していたセッション」が見つかり、利用者の判断を待っている状態（第11章）。 |

### 4.2 基本挙動

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TIM-001** | **MUST** | タイマーの同期は「残りカウントダウン秒数」ではなく、**終了絶対時刻（`sessionEndAt`）** を基準に行うこと。 |
| **REQ-TIM-002** | **MUST** | 一時停止時はその時点の残り時間を `remainingSeconds` に保持し、再開時に「現在時刻＋残り時間」から `sessionEndAt` を再計算すること。 |
| **REQ-TIM-003** | **MUST** | `sessionEndAt` が変化するあらゆる操作（開始・再開・一時停止・延長・スキップ・中断）の直後に、状態をクライアントへ配信すること。**設定変更およびプリセット切替は `sessionEndAt` を変化させない**（REQ-CFG-003）。 |
| **REQ-TIM-004** | **MUST** | セッション長は、**セッション開始時点で有効だったプリセット**（`TimerContext.sessionPresetId`）の値で決定し、開始後のプリセット切替・編集によって変化させないこと。 |
| **REQ-TIM-005** | **MUST** | 実行中セッションの経過時間は、`sessionStartedAt` からの壁時計差分ではなく、**一時停止累計（`accumulatedPausedSeconds`）を差し引いた正味稼働時間**として算出すること。ログの「実経過時間」（REQ-LOG-010）および 60 秒判定（REQ-TIM-032）はこの値を用いる。 |

### 4.3 セッション遷移

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TIM-010** | **MUST** | セッションが終了時刻に到達した場合、`RunState` を `FINISHED` に遷移させ、**自動では次のセッションを開始しないこと**（既定動作）。利用者が明示的に次へ進む。 |
| **REQ-TIM-011** | **SHOULD** | 有効なプリセットの `autoAdvance` が有効な場合に限り、`FINISHED` 到達後に自動で次のセッションを開始できること。`Standard` プリセットでは無効。**REQ-TIM-011 を実装しない場合、4.5 表の「`autoAdvance` 時」の記述は無視してよい。** |
| **REQ-TIM-012** | **MUST** | `nextSessionType` は「**現在のセッションが正常完了したと仮定したときに次に来る種別**」として常時算出し、状態に含めて配信すること。`IDLE` では「直前のセッションが正常完了したと仮定した場合」を用いる。<br>・現在（または直前）が `WORK` → `loopCount + 1` が `longBreakInterval` の**倍数**なら `LONG_BREAK`、それ以外は `SHORT_BREAK`<br>・現在（または直前）が `SHORT_BREAK` / `LONG_BREAK` → `WORK`<br>・セッションが一度もない（起動直後・リセット直後）→ `WORK` |
| **REQ-TIM-015** | **MUST** | REQ-TIM-012 の倍数判定は `loopCount + 1`（＝完了後の値）に対して行い、`loopCount` が 0 のときに `LONG_BREAK` を導いてはならない。 |
| **REQ-TIM-016** | **MUST** | `WORK` が**スキップまたは中断**された場合（周回数が加算されない場合）、その直後の `nextSessionType` は `SHORT_BREAK` とすること。REQ-TIM-012 の倍数判定を適用しない。 |
| **REQ-TIM-017** | **MUST** | REQ-NTF-002 の事前スケジュール通知に載せる「次に行うべきセッション種別」は、**セッション開始時点の `nextSessionType`** を用いること。以降に値が変化した場合は REQ-NTF-003(b) により再スケジュールする。 |
| **REQ-TIM-013** | **MUST** | 利用者は `nextSessionType` の推奨に従わず、**任意の種別を明示的に開始できること**。この場合も REQ-TIM-012 の規則で次の `nextSessionType` を再計算すること。 |

**背景・理由:** スキップした `WORK` の後に `LONG_BREAK` を与えると、集中していないのに長い休憩に入る。スキップ後は常に `SHORT_BREAK` を提案する。

### 4.4 周回数（loopCount）

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TIM-020** | **MUST** | 周回数の加算は、`WORK` セッションが**正常完了**（終了絶対時刻に到達して `FINISHED` へ遷移）した時点でのみ行うこと。休憩の完了、スキップ、中断では加算しないこと。 |
| **REQ-TIM-021** | **MUST** | 延長された `WORK` セッションも、最終的に終了時刻に到達すれば正常完了として1回加算すること（延長回数によらず1回）。 |
| **REQ-TIM-022** | **MUST** | 周回数は以下のいずれかの条件で 0 にリセットすること：(a) 利用者による明示的なリセット操作、(b) `lastSessionEndedAt` から `idleResetHours`（既定12時間）以上経過した状態で新たなセッションを開始したとき、(c) `logicalDate` が変化した状態で新たなセッションを開始したとき。 |
| **REQ-TIM-023** | **MUST** | 「論理日」は `logicalDayStartHour`（既定 04:00、ローカルタイムゾーン）を境界として定義すること。 |
| **REQ-TIM-024** | **MUST** | `LONG_BREAK` の完了によって周回数をリセットしないこと。`loopCount` は REQ-TIM-022 の条件でのみ 0 に戻る。 |
| **REQ-TIM-025** | **MUST** | UI 上の周回表示（REQ-UIX-003）は `((loopCount − 1) mod longBreakInterval) + 1` を分子とし、`loopCount` が 0 のときは「0 / n」と表示すること。分子が `longBreakInterval` を超える表示（「5 / 4」等）を行ってはならない。 |

### 4.5 操作の定義

| 操作 | 意味 | 周回数 | ログ記録 | 遷移先 |
| :---- | :---- | :---- | :---- | :---- |
| **一時停止 / 再開** | 残り時間を保持して停止・再開 | 影響なし | しない | `RUNNING` ⇄ `PAUSED` |
| **スキップ** | 現セッションを完了扱いにせず終了し、次のフェーズへ進む | 加算しない | `skipped` として記録 | `IDLE`（`autoAdvance` 時は次セッションの `RUNNING`） |
| **中断** | 現セッションを破棄する | 加算しない | `aborted` として実経過時間を記録 | `IDLE` |
| **リセット** | 周回数を 0 に戻す。実行中セッションがあれば中断を伴う | **0 にリセット** | 中断分を記録 | `IDLE` |
| **延長** | 終了時刻を後ろへずらす | 影響なし | 累積延長時間を併記 | 状態は変わらない（`FINISHED` からは `RUNNING` へ戻る） |

### 4.7 延長（フロー維持）

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TIM-040** | **MUST** | `WORK` セッションに対し、**操作時点で有効なプリセット**の `extendSeconds`（`Standard` プリセットでは5分）だけ終了時刻を延ばす「延長」操作を提供すること。**加算の起点は現在時刻ではなく、そのセッションの終了予定時刻とする**（終了予定 10:00 のセッションを5分延長すると、押した時刻にかかわらず 10:05 まで延びる）。`PAUSED` では `sessionEndAt` ではなく `remainingSeconds` に加算する。 |
| **REQ-TIM-046** | **MUST** | 延長操作を受け付けるのは、次の**延長受付ウィンドウ**内に限ること。ウィンドウ外の `extend` は `error`（`code: extendWindowClosed`）を返し、UI 上でもボタンを無効化すること。<br>・`RUNNING`: 残り時間が **5 分以下**（`sessionEndAt − now ≤ 300`）<br>・`PAUSED`: `remainingSeconds ≤ 300`<br>・`FINISHED`: 終了から **1 分以内**（`now − finishedAt ≤ 60`） |
| **REQ-TIM-041** | **MUST** | 延長は REQ-TIM-046 のウィンドウ内であれば回数無制限で実行可能とし、累積延長時間を `extendedSeconds` として保持・記録すること。 |
| **REQ-TIM-042** | **MUST** | `FINISHED` からの延長は、**加算済みの周回数を 1 減算**したうえでセッションを `RUNNING` へ戻すこと。ログはこの時点でまだ書き込まれていない（REQ-LOG-018）ため、ログに対する取り消し処理は不要かつ行ってはならない。 |
| **REQ-TIM-043** | **MUST** | `FINISHED` 到達後にセッションを確定せず保留する猶予は、`finishedAt` から **1 分以内**とし、REQ-TIM-046 の延長受付ウィンドウと一致させること。**`autoAdvance` が有効な場合、次セッションの自動開始によって猶予は即座に終了する**（REQ-TIM-011 を選ぶことは猶予を放棄することを意味する）。UI 上でその旨を示すこと。猶予を超えた時点でセッションを確定し（ログ書き込み・周回数の確定）、延長操作を無効化すること。**猶予時間はプリセットに含めず、全プリセット共通の固定値とする。** |
| **REQ-TIM-044** | **MUST** | 休憩セッション（`SHORT_BREAK` / `LONG_BREAK`）の `FINISHED` には延長猶予を設けず、到達と同時にログを確定すること。休憩に対する延長操作は提供しない。 |
| **REQ-TIM-045** | **MAY** | 終了時刻を設けない「無制限モード（ストップウォッチ）」を提供する。この場合、経過時間を計測し、利用者が明示的に終了した時点で `WORK` の**正常完了**として扱い、周回数を加算する。 |

**背景・理由:** 「過集中（フロー状態）の維持」は固定長タイマーと本質的に緊張関係にある。集中が続いているときに強制的に中断させないための逃げ道が必要。一方、休憩を延長できると休憩が際限なく伸びるため、延長は `WORK` に限定する。

**背景・理由（受付ウィンドウと起点）:** 延長の起点を「押した時刻」にすると、終了に気づかず4分放置してから押しても満額の延長が得られてしまう。これは集中と休憩を繰り返す手法の趣旨に反する。**終了予定時刻を起点に固定し、受付を終了後1分までに絞る**ことで、「区切りを意識している人だけが延長できる」構造にする。<br>この設計は、終了に気づくのが遅れる問題を延長操作の自由度で埋め合わせない、という判断に基づく。遅れが問題なのであれば、埋め合わせるべきは**終了の予告通知**（REQ-NTF-007 / 020〜022）であって延長ではない。<br>受付ウィンドウが終了後1分までであり `extendSeconds` の下限が1分であるため、**延長後の終了時刻が現在時刻より前になることはない**（REQ-TIM-040 の起点固定が破綻しない）。

**背景・理由（猶予の固定値化）:** 猶予時間をプリセットごとに変えられるようにすると、猶予中にプリセットを切り替えた際に「猶予が既に終わっていた」状態が発生し、確定済みかどうかの判定が端末間でずれる。

## 6. タスク連携仕様

**対象は Markdown ファイルであって、特定のツールではない**（`decisions/0023-markdown-first-not-obsidian-first.md`）。
Obsidian の保管庫でも、Logseq のグラフでも、ただのフォルダに置かれた1枚の `.md` でもよい。
本章で「Obsidian」に言及するのは、**その記法や挙動を例として説明するときだけ**である。

### 6.1 基本原則

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TSK-001** | **MUST** | 指定された `Task.md` は読み取り専用として扱い、本システムからの書き込み・編集を一切行わないこと。 |
| **REQ-TSK-002** | **MUST** | Mac 側で `Task.md` のファイル変更を常時監視（`DispatchSource` / FSEvents）し、変更検知時は 300ms のデバウンスを挟んで自動で再読み込みし、iPhone へ最新リストを配信すること。 |
| **REQ-TSK-003** | **MUST** | 選択中タスクの情報はアプリの状態としてのみ保持し、Markdown 側へ反映しないこと。 |
| **REQ-TSK-004** | **MUST** | 読み込まれたタスク一覧は、Mac・iPhone のどちらの画面からでも閲覧・選択可能とすること。 |
| **REQ-TSK-005** | **MUST** | 監視対象ファイルのパスは設定画面から選択でき、**保管場所に依存しないこと**（Obsidian の保管庫、Logseq のグラフ、任意のフォルダのいずれでもよい）。 |

### 6.2 パース規則

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TSK-010** | **MUST** | タスクとして認識するのは、正規表現 `^\s*[-*+]\s+\[(.)\]\s+` に一致する行のみとすること（リストマーカーは `-` / `*` / `+`、チェックボックス内は任意の1文字）。それ以外の箇条書きや本文はタスクとして扱わない。**ツール固有のタスク記法（Logseq の `TODO` / `DOING` / `NOW` マーカー等）は認識しないこと**（`decisions/0025-standard-checkbox-syntax-only.md`）。 |
| **REQ-TSK-011** | **MUST** | 見出し（`#` 〜 `######`）をセクションとして認識し、タスク一覧を見出しごとにグループ化して表示すること。見出しより前にあるタスクは未分類のグループとする（表記は第16章）。 |
| **REQ-TSK-012** | **MUST** | チェックボックス内が**半角スペース以外**の文字である場合を「完了済み」と判定すること（`[x]`、`[X]`、`[-]`、`[/]` 等をすべて完了として扱う）。完了済みタスクは既定でリストから除外し、設定 `showCompletedTasks` で表示に切り替えられること。 |
| **REQ-TSK-013** | **MUST** | インデントされた子タスクを階層として認識し、親子関係を保持すること。**ファイル内で最初に検出したインデント（スペース数またはタブ）を1段分と定め、以降その倍数で深さを判定すること。** 倍数に満たない中途半端なインデントは、直近の浅い方の深さに丸めること。 |
| **REQ-TSK-014** | **MUST** | 子タスクも独立して選択可能とすること。表示上は親の下に字下げして並べる。 |
| **REQ-TSK-015** | **SHOULD** | タスク本文中の記法（外部リンク `[text](url)`、強調、インラインコード、および一部のツールが解釈する内部リンク `[[...]]` とタグ `#tag`）を表示用にレンダリングまたは除去し、生の記法をそのまま表示しないこと。 |
| **REQ-TSK-016** | **SHOULD** | パース結果が 0 件だった場合、タスクが見つからないことと、**読み取る記法の例**（`- [ ] Write the spec` のような英語のサンプル）を UI に表示すること。読み取る記法は REQ-TSK-010 が定めるものに限られるため、**何を書けば認識されるかを画面で示すこと**が、そのまま利用者への契約になる。 |

### 6.3 タスク識別子（ID）

Markdown には本来、行を一意に識別する仕組みがない。本システムは以下のハイブリッド方式を採る。
**ブロック ID は任意の互換機能である。** 付いていれば使い、無ければ本文のハッシュで代替する。
ブロック ID を書く道具（Obsidian 等）の利用を前提としてはならない。

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TSK-020** | **MUST** | タスク行の末尾にブロック ID（`^abc123` 形式。Obsidian が対応する記法）が存在する場合、それを `stableId` として採用すること（種別: `blockId`）。**ツール固有のプロパティ（Logseq の `id::` 等）は採用しない**（`decisions/0025`）。 |
| **REQ-TSK-021** | **MUST** | ブロック ID が存在しない場合、`正規化本文の SHA-256 ハッシュ（先頭16桁）` ＋ `同一ハッシュ内での出現順` を `stableId` として採用すること（種別: `contentHash`）。 |
| **REQ-TSK-022** | **MUST** | 正規化は次の順で行うこと：(1) リストマーカーとチェックボックスを除去、(2) 前後の空白を除去、(3) 内部リンク・外部リンクを表示テキストへ置換、(4) タグ・絵文字・強調記号を除去、(5) 連続する空白を単一のスペースへ統合、(6) Unicode 正規化（NFKC）。 |
| **REQ-TSK-023** | **MUST** | ID の種別（`blockId` / `contentHash`）を `TaskItem` に保持し、UI 上でブロック ID を持つタスクを識別できるようにすること。 |
| **REQ-TSK-024** | **SHOULD** | 設定画面またはヘルプに、行末へブロック ID（`^abc123`）を付ければ文言を修正しても選択が維持される旨を案内すること。**特定のツールの利用を前提とした書き方をしないこと**（付与を自動化できる道具がある、という補足に留める）。 |

### 6.4 選択中タスクの消失

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-TSK-030** | **MUST** | 再読み込みの結果、選択中タスクの `stableId` が**ファイル全体のどこにも（完了済み行を含めて）存在しなくなった**場合、`selectedTaskState` を `missing` とし、**そのタスクがファイル上に見つからないこと**を UI に示すこと。**タイマー実行中は自動的に選択を解除してはならない。** |
| **REQ-TSK-034** | **MUST** | `selectedTaskState` の判定順序は次のとおりとすること。(1) 未選択なら `none`、(2) ファイル内に存在し完了済みなら `completed`、(3) ファイル内に存在し未完了なら `present`、(4) いずれでもなければ `missing`。**`showCompletedTasks` の設定値は本判定に影響してはならない**（表示上除外されているだけのタスクを `missing` と誤判定しないため）。 |
| **REQ-TSK-031** | **MUST** | 利用者が明示的に選択を解除するか、別のタスクを選択するまで、その状態を維持すること。実績ログには最後に既知だった本文を記録すること。 |
| **REQ-TSK-032** | **SHOULD** | 消失したタスクと、同じ再読み込みで新規に出現したタスクとの間で正規化本文の類似度（Levenshtein 距離ベース）を計算し、閾値（本文長の 30% 以内）を満たす候補が一意に定まる場合は、同一タスクとみなして選択を自動追従させること。この追従が発生した際は UI に控えめな通知を表示すること。 |
| **REQ-TSK-033** | **MUST** | `selectedTaskState` が `completed` に変化した場合、タイマー実行中であれば選択を維持したうえで完了済みになったことを示し、セッション終了時に次のタスク選択を促すこと。 |
| **REQ-TSK-035** | **MUST** | `contentHash` 方式（REQ-TSK-021）では、同一本文の重複タスクのうち先行するものが削除されると後続の `stableId` が変化する。この場合も REQ-TSK-032 の追従処理の対象とすること。 |
| **REQ-TSK-036** | **MUST** | `selectTask` で現在の一覧に存在しない `stableId` を受信した場合、`taskNotFound` を返し選択を変更しないこと。 |
| **REQ-TSK-037** | **MUST** | REQ-ERR-003 により読み込みを打ち切った場合、`taskList` メッセージに打ち切りの有無と読み込んだ件数を含め、UI に表示できるようにすること。 |

**背景・理由:** タスク ID の安定性は本システム最大の実装上の難所である。利用者は作業中にエディタでタスク文言を推敲することが十分ありうるため、そのたびに選択が外れタイマーとの紐付けが失われる体験は避けなければならない。

### 7.1 出力先と形式

| **REQ-LOG-004** | **MUST** | 書き込みは原子的に行うこと（一時ファイルへ書き出し後に `rename`）。書き込み前にファイルを再読み込みし、外部変更を取り込んでから追記すること。**出力先はファイル単体ではなくフォルダとして選ばせ、フォルダに対するアクセス許可を得ること。** 理由は `rename` の制約ではなく**ブックマークの及ぶ範囲**である —— **ファイル単位のブックマークでは、隣に一時ファイルを作ることも、元のファイルを差し替えることもできない**（どちらも親ディレクトリへの書き込みを要する。`CONTEXT.md` §2 に実測がある）。**v2.23 で理由を訂正した**（旧文は「一時ファイルを同一ディレクトリに置く必要があるため」としていたが、[platform/0007](platform/0007-atomic-replacement-is-a-volume-constraint.md) によりこれは誤り）（`decisions/0015-log-folder-scoped-access.md`）。 |
| **REQ-LOG-005** | **MUST** | 書き込みに失敗した場合はアプリ内のキューに保持して再試行し、タイマー動作を止めないこと。**通知の条件は REQ-ERR-004 に従う**（`decisions/0039-failures-that-come-and-go-still-count.md`）。**状態ファイルが使えず保存が止まっている間（REQ-ERR-017）は、キューの永続化を行えない。この間に限り本条文の永続化義務は適用しない** — 上書きで壊さないことを優先する（`decisions/0036-an-unreadable-state-file-is-set-aside.md`）。**このキューの対象は書き込みの失敗であり、`logFolderPath` の未設定はこれに当たらない**（REQ-LOG-002 / `decisions/0033-unset-log-path-records-nothing.md`）。**このキューは永続化すること**（REQ-PER-001）。確定時に `committedAt` が設定される（REQ-LOG-019）ため、キューを失うとそのセッションの記録は二度と書かれない。 |

### 7.2 記録内容

各セッション（`WORK` / `SHORT_BREAK` / `LONG_BREAK`）の終了・スキップ・中断時に1行を追記する。

**出力形式（例）** — `[ ]` 内はセッション開始時に有効だったプリセット名。`Deep Work` は利用者が自作したプリセットの例。
アプリが生成する語は英語で固定する（REQ-UIX-038）。**タスク名とプリセット名は利用者由来であり、そのまま出力する**（この例が英語なのは例だからである）。

```markdown
## 2026-08-24 (Mon)

- 09:00–09:25 WORK 25m ✅ Loop 1/4 [Standard] — Review the spec
- 09:25–09:30 SHORT_BREAK 5m ✅ [Standard]
- 09:32–10:04 WORK 32m ✅ Loop 2/4 (+7m extended) [Standard] — Protocol design
- 10:04–10:09 SHORT_BREAK 5m ⏭ Skipped [Standard]
- 10:15–11:05 WORK 50m ✅ Loop 2/2 [Deep Work] — Protocol design
- 11:05–11:35 LONG_BREAK 30m ✅ [Deep Work]
- 11:35–11:43 WORK 8m ⏹ Stopped [Deep Work] — Protocol design
```

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-LOG-010** | **MUST** | 1行に含める情報：開始時刻、終了時刻、セッション種別、**実経過時間（REQ-TIM-005 の正味稼働時間）**、終了理由（完了/スキップ/中断）、プリセット名（`sessionPresetName`）、選択中タスク名（`WORK` のみ、`selectedTaskSnapshot`）。 |
| **REQ-LOG-017** | **MUST** | セッションが属する論理日は、**`sessionStartedAt` を基準**に決定すること。論理日境界をまたいだセッションは開始側の日付見出しに記録する。 |
| **REQ-LOG-018** | **MUST** | ログの書き込み（確定）は次のいずれかの時点で行うこと。<br>・`WORK`: 延長猶予の満了（REQ-TIM-043）、次セッションの開始、`abort`、`resetLoopCount` のいずれか早い方<br>・休憩: `FINISHED` への到達と同時（REQ-TIM-044）<br>・スキップ・中断: 操作と同時<br>・`confirmRestoredSession` による `complete` / `discard` の応答時（REQ-PER-003）<br>・`PENDING_DECISION` 未応答のまま `logicalDate` が変化したとき（REQ-PER-004） |
| **REQ-LOG-019** | **MUST** | 確定処理は `committedAt` を見て**冪等**に行うこと。`committedAt` が非 null のセッションに対して確定処理を再実行してはならない。確定に成功した時点で `committedAt` を設定し、永続化すること。**`logFolderPath` が未設定で書き込みを行わなかった場合も `committedAt` を設定すること**（REQ-LOG-002 / `decisions/0033`）。立てないと復帰時に REQ-PER-003(d) へ落ち、記録先が無いまま確認を求めることになる。 |
| **REQ-LOG-023** | **MUST** | ログに記録するタスク名は、**セッション開始時点で選択されていたタスク**（`selectedTaskSnapshot`）とすること。セッションが `FINISHED` / `PENDING_DECISION` にある間に選択が変更されても、確定するログ行には反映しないこと。 |
| **REQ-LOG-011** | **MUST** | `WORK` の正常完了行には、そのセッション完了後の周回数を `n / longBreakInterval` の形式で含めること。**`n` は REQ-TIM-025 と同じ剰余表現**とし、UI の表示と一致させること。 |
| **REQ-LOG-012** | **MUST** | 延長が行われた場合、累積延長時間を併記すること。 |
| **REQ-LOG-013** | **SHOULD** | タスク名は内部リンク記法（`[[...]]`。Obsidian / Logseq などが解釈する）ではなく、リンクにならないプレーンテキストとして出力すること。ただし設定でリンク化を選べること。既定はプレーンテキスト。 |
| **REQ-LOG-014** | **SHOULD** | 設定 `logDailySummary` が有効な場合、論理日の最初の書き込み時に前日の日次サマリ行（合計 Work 時間・完了周回数）を追記すること。既定は無効。 |
| **REQ-LOG-015** | **MAY** | 集計しやすいインラインフィールド形式（`(duration:: 25m)` 等）での出力を選択できる。**特定のツールを前提としない**（`decisions/0023-markdown-first-not-obsidian-first.md`）。 |
| **REQ-LOG-016** | **MUST** | `presetEditedDuringSession` が真の場合（＝セッション開始後にそのプリセットの A 群項目が編集された場合）、プリセット名の後に `*` を付すこと。プリセット名の記録義務は REQ-LOG-010 に一本化する。 |

### 7.3 運用上の制約

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-LOG-020** | **MUST** | ログファイルは、本システムが追記中に**エディタ側で同時編集されると競合しうる**。ログファイルを開いたまま編集しない運用を前提とし、その旨を設定画面に明記すること（特定のツール名を挙げないこと）。 |

### 8.2 iPhone 集中表示ビュー

v1.0 の「StandBy モード」を実現可能な形式に再定義する。

> **技術的補足:** iOS 純正の StandBy（充電中・横向き設置時の全画面表示）には、ウィジェットまたは対応する一部のシステム機能しか表示できず、任意のアプリを常時全画面表示することはできない。したがって本システムでは「アプリ内の常時表示ビュー」と「Live Activity」の2系統で同等の体験を実現する。

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-UIX-010** | **MUST** | アプリ内に「集中表示ビュー」を設けること。残り時間は**画面短辺の 40% 以上の文字高**で表示し、**副次情報の文字高の 4 倍以上**とすること。**ここでいう「文字高」はフォントサイズを指す。**字面の高さと解すると、縦向きでは `05:12` の5字が横幅に収まらず成立しない（2026-08-27、実機で確認のうえ確定）。副次情報はセッション種別・選択中タスク名・周回数、および接続状態インジケータ（REQ-UIX-004）のみに限ること。**ここでいう副次情報とは、この画面に常時表示されるものを指す。** 操作に応じて現れ、数秒で消える案内（戻り方の案内、操作が受理されなかったことの通知など）はこれに当たらない。**ただし色を帯びた地は使わない**（REQ-UIX-046）。 |

| **REQ-UIX-012** | **MUST** | 集中表示ビュー中は自動画面ロックを抑止すること（`isIdleTimerDisabled`）。ただしビューを離れた際、およびアプリがバックグラウンドへ移行した際は必ず解除すること。 |

### 8.3 Live Activity / ダイナミックアイランド

> **前提とするプラットフォームの制約:** Live Activity は **(a) 開始は原則としてアプリがフォアグラウンドにある間に限られ**、**(b) 更新はアプリが running である間しか行えない**（(a) の門のほうが狭い）。iPhone が **suspend されている間はアプリのコードが実行されない**。したがって、**Mac 側で起きた予定外の状態変化**（一時停止・再開・延長・スキップ・中断）を、その時点で Live Activity へ反映することはできない。**残り時間の表示はこの制約の対象外である**（REQ-UIX-021）。本節はこの制約を前提に設計する。
>
> **事実の出典は `docs/PLATFORM.md`「Live Activity — 開始と更新の門」**（調査: [`docs/platform/0002`](platform/0002-live-activity-background-start-and-suspend.md)）。**この節で条文がプラットフォームの事実を抱えない**（`decisions/0038-platform-facts-are-not-the-specs-job.md`）。

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-UIX-020** | **SHOULD** | iPhone アプリが**フォアグラウンドにある状態**でセッションが開始された場合、ActivityKit の Live Activity を開始すること。バックグラウンド中に Mac 側で開始されたセッションについては、次にアプリがフォアグラウンドへ復帰した時点で開始すること。 |
| **REQ-UIX-021** | **MUST** | 残り時間の表示には `Text(timerInterval:pauseTime:countsDown:)` を用い、`sessionEndAt` に基づいてシステム側で自律的に更新させること。アプリからの毎秒更新を行ってはならない。 |
| **REQ-UIX-029** | **SHOULD** | 一時停止をアプリが running の間に検知できた場合は、`pauseTime` を設定した update により停止表示へ切り替えること。**検知できない場合（アプリが suspend 中）は `staleDate` の失効により `isStale` 表示へ移行することで足りる**（REQ-UIX-023）。 |
| **REQ-UIX-022** | **SHOULD** | アプリが running である間に状態が変化した場合（開始・一時停止・再開・延長・セッション種別変更）、Live Activity を更新すること。セッション終了・中断時は終了させること。 |
| **REQ-UIX-023** | **MUST** | Live Activity の `ActivityContent.staleDate` を、**次にアプリが状態を確認できる保証がない時刻**（既定では更新時刻＋90秒）に設定すること。`context.isStale` が真のとき、Live Activity 上に情報が古い可能性があることを明示すること。**ダイナミックアイランドのコンパクト表示・ミニマル表示では、文言を置く余地がないため注意記号で示してよい。** また、`isStale` の切り替わりは OS が決めるため期限どおりとは限らない（実測で4分遅れ）。**接続が切れたことはクライアントが知っているので、`isStale` とは別に自分で示すこと。****アプリが running かつ接続が生きている間は、状態が変化していなくても `staleDate` を押し出し続けること**（既定 60 秒間隔）。状態同期は変化時のみ行われる（REQ-COM-006）ため、押し出さなければ正常動作中でも 90 秒で陳腐化表示になる。 |
| **REQ-UIX-024** | **SHOULD** | Live Activity 上に「一時停止 / 再開」ボタンを `LiveActivityIntent` として配置してよい。`perform()` は**アプリ本体のプロセス**で実行されるため、その中で Mac への再接続とコマンド送信を試みること。接続に失敗した場合は Live Activity を `isStale` 表示へ切り替え、状態を変更したかのように見せてはならない。**この再接続と失敗の提示を実装しない限り、ボタンを置いてはならない**（`decisions/0030-live-activity-is-display-only.md`）。**iPhone が suspend されている間はアプリのコードが実行されないため**、実装がなければボタンは常に無反応になる（v2.21 で根拠を訂正。`docs/PLATFORM.md`）。 |
| **REQ-UIX-025** | **MUST** | Live Activity へ渡すデータは **4KB 以内**に収めること。**上限は `ActivityAttributes`（静的）と `ContentState`（動的）の合計に掛かる。動的データだけを 4KB に収めても、この要件を満たしたことにならない**（v2.20 で訂正。`docs/PLATFORM.md`）。測るのは**シリアライズ後**の大きさである。タスク名は表示可能長で切り詰めること。 |
| **REQ-UIX-026** | **MUST** | **Live Activity からネットワークにアクセスしないこと**（サンドボックス上不可能。Apple が明記している）。表示に必要な情報はすべて `ActivityAttributes` / `ContentState` として渡すこと。**この禁止は Live Activity に掛かるのであって、ウィジェット拡張という入れ物に掛かるのではない**（v2.20 で訂正。ウィジェットのネットワークアクセスは Apple が手順を文書化している。`docs/PLATFORM.md`）。**境界は表示面ではなくプロセスである** — `LiveActivityIntent.perform()` はアプリ本体のプロセスで走るため、この禁止の対象外（REQ-UIX-024）。 |
| **REQ-UIX-027** | **MUST** | Live Activity の配色は 8.5 のトークンをそのまま適用しないこと。8.5.3 の保証は `--bg` を地とした場合のものであり、ロック画面の器はそれとは別の背景を持つ（`PLATFORM.md`「Live Activity」）。<br>・**ロック画面**: 器の既定背景を用いる場合は、前景をシステムに委ねてよい。**カスタム背景色を敷く場合は、ライト・ダークの両モードで通用する組み合わせを自分で保証すること** — システムは背景色から前景色を導出しない。<br>・**Always-On の輝度低下時はダークモードとして描かれる。** `isLuminanceReduced` で検出できる。<br>・**ダイナミックアイランド**: 背景は不透明な黒で固定であり、変更できない。**ここは固定値でコントラストを組める。** |
| **REQ-UIX-028** | **MUST** | Live Activity の継続時間上限（アクティブ8時間、ロック画面残留を含め最大12時間）を超えた場合、アプリ復帰時に新しい Live Activity を開始すること。この上限は無制限モード（REQ-TIM-045）を実装する場合にのみ実務上の問題となる。 |

**Live Activity は「セッション終了を知らせる手段」ではない。** 終了の通知は第5章のローカル通知が担い、Live Activity は**アプリが動いている間の残り時間の可視化**に徹する。両者を独立させることで、Live Activity が更新できない状況でも通知は必ず届く。

**背景・理由（MUST → SHOULD への格下げ）:** v2.3 では REQ-UIX-020/022 を MUST としていたが、**(b) と suspend 中はコードが実行されないこと**により、常には満たせない。満たせない要件を MUST に置くと、リリース可否の判断基準が機能しなくなる。**格下げの根拠は (b) と suspend であって、開始経路の有無ではない**（v2.19 で訂正。旧文は「例外は APNs のみ」という誤った前提に依拠していた）。サーバーを使わない開始経路については第15章 FUT-013 を参照。


### 8.4 Mac 側 UI

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-UIX-030** | **MUST** | メニューバーに常駐し、既定（`timeAndType`）では残り時間とセッション種別を常時表示すること。メニューバー内の配色は REQ-COL-022 に従うこと。 |
| **REQ-UIX-035** | **MUST** | メニューバーのテンプレート画像は、**セッションの実行状態**（待機 / 進行中 / 一時停止）を形状で区別して示すこと。**色だけに情報を載せないため**（REQ-COL-022）、状態は形状で表現する。**接続状態をこの画像に載せてはならない。** **iPhone は背面へ回ればやがて suspend され、その間はアプリのコードが実行されない**（`docs/PLATFORM.md`）。接続は生きていても読み手がいないため、接続を印に載せると通常運用のほとんどの時間が「未接続」の表示になり、実行状態が読めなくなる（`decisions/0031-the-menu-bar-mark-shows-the-session.md`）。 |
| **REQ-UIX-031** | **MUST** | **メニューは伝達の場所も兼ねる。ただし出してよいのは、取り返しのつかない状態と緊急性の高い場合に限る**（`decisions/0037-the-menu-is-the-last-place-a-message-can-reach.md`）。完了の報告・進捗・統計は置かない。**操作の上に読み物を積まない。** メニューバーのドロップダウンは、**危険度で階層を分けること**（`decisions/0029-menu-bar-as-a-control-surface.md`）。<br>・**直下に置いてよい**: 一時停止 / 再開、次のセッションを開始、スキップ、プリセット切替、設定を開く、メインウィンドウを開く、終了<br>・**確認を1段はさむこと**: 中断、周回リセット<br>・**サブメニューに置いてよい**: タスク選択、外観、メニューバーの表示密度<br>・**置いてはならない**: プリセットの編集、ファイルのパス変更、ペアリング（不可逆であるか、アプリの外の資産・他の端末に及ぶため）<br>読むだけの情報は制限の対象ではない。 |
| **REQ-UIX-032** | **SHOULD** | メニューバーの表示密度を `menuBarDisplayMode`（9.3）で選択できること。`timeAndType`（既定）/ `timeAndTask` / `timeOnly` / `iconOnly` の4値とする。 |
| **REQ-UIX-033** | **SHOULD** | グローバルキーボードショートカットで「一時停止 / 再開」「**次のセッションを開始**」「**スキップ**」を実行できること（`decisions/0029-menu-bar-as-a-control-surface.md`）。**中断・リセットには割り当てないこと**（確認をはさめないため）。**既定では割り当てず、利用者が任意の組み合わせを設定できること。**修飾キーを含まない割り当ては受け付けないこと。他アプリに専有されていて登録できなかった場合は、その旨を設定画面に示すこと（`decisions/0016-standard-settings-and-hotkeys.md`）。**アクセシビリティ権限を要求しない手段で実装すること。** |
| **REQ-UIX-034** | **MAY** | Mac 側にも常時最前面表示のフローティングウィンドウ（コンパクトな残り時間表示）を提供する。 |

**背景・理由:** 視界に入る情報を極限まで減らし、かつ必要な時に一目で残り時間がわかることで、過集中を邪魔しない UI/UX を構築するため。

### 8.5 カラーパレット

#### 8.5.1 設計方針

| 方針 | 内容 |
| :---- | :---- |
| **紙とインク** | 暖色ニュートラル（OKLCH 色相 82°）を地とし、彩度を抑えたインクの色を載せる。純白・純黒を使わない。 |
| **OKLCH で設計** | 全トークンを OKLCH（知覚的均等色空間）で定義し、hex は算出結果とする。明度の刻みが知覚上も均等になり、ライト／ダークの対称性が保たれる。 |
| **役割で持つ** | トークンは色名ではなく役割（`session-focus`、`danger` 等）で参照する。色相の変更がコード変更にならない。 |
| **識別を計測で担保** | セッション3色は、2型・1型色覚シミュレーション下での OKLab 距離を計測し、最小 ΔE 14 以上を確保する（8.5.5）。 |
| **段階を持たせる** | 各色相は `subtle` / `line` / `graphic` / `solid` / `text` の5役に分解する。単一の「アクセント色」を用途ごとに使い回さない。 |

#### 8.5.2 色相と役割

| 名称 | OKLCH 色相 | 役割 |
| :---- | :---- | :---- |
| **Neutral** | 82° | 背景・面・境界・テキスト |
| **Ink**（藍） | 235° | **Focus（Work）** / フォーカスリング / 主要アクション |
| **Sage**（青磁） | 142° | **Short Break** / 成功 |
| **Ochre**（黄土） | 66° | **Long Break** / 注意・警告 |
| **Clay**（弁柄） | 30° | 破壊的操作 / エラー / 未接続 |

#### 8.5.3 トークン定義

各色相は5役に分解する。用途を取り違えるとコントラスト基準を割るため、役ごとの用途は厳密に守ること。

| 役 | 用途 | 保証されるコントラスト |
| :---- | :---- | :---- |
| `-subtle` / `-subtle-hover` | 色を帯びた面（バッジ、バナー、選択行の地） | 背景に対し 1.10–1.60（面として認識できる最小差） |
| `-line` | 色を帯びた境界線・区切り | 背景に対し 2.00–2.45 |
| `-graphic` | **意味を持つ非テキスト図形**（進行リング、状態ドット、グラフ） | 背景に対し **3.0 以上**（WCAG 1.4.11） |
| `-solid` / `-solid-hover` | **文字が乗る塗り**（ボタン、チップ） | 背景に対し 4.5 以上、かつ `-on-solid` との間に 4.5 以上 |
| `-text` | 背景の上に置くテキスト・アイコン | **`--bg` / `--bg-sunken` / `--surface` / `--surface-raised` の4面すべてに対し 4.5 以上**（最小 4.58） |

#### 8.5.5 検証結果

**色覚多様性下での識別性**（セッション3色の `-graphic` トークン、OKLab ΔE ×100。10 未満で混同リスク）

シミュレーションは **Viénot, Brettel & Mollon (1999) を線形 sRGB に適用**したもの。
下表は `MdoroCore` の自動テスト（REQ-COL-020）が実際に算出する値であり、テストを走らせれば再現できる。
**モデルを差し替えると数値は動く。動かしてよいのは数値であって、判定基準（ΔE 14）ではない。**

| モード | 視覚型 | Focus / Short | Focus / Long | Short / Long |
| :---- | :---- | :---- | :---- | :---- |
| ライト | 一般 | 15.3 | 21.4 | 18.7 |
| ライト | 2型（deutan） | 15.8 | 20.2 | 15.0 |
| ライト | 1型（protan） | **14.8** | 21.2 | 20.3 |
| ダーク | 一般 | 16.6 | 22.5 | 21.9 |
| ダーク | 2型（deutan） | 17.1 | 21.8 | 18.8 |
| ダーク | 1型（protan） | 16.0 | 22.5 | 24.1 |

最小値は 14.8（ライト・1型の Focus/Short 間）。色相だけでなく明度にも意図的に段差をつけているため、色相が失われても明度で識別できる。

**明度の段差（絶対輝度、`-graphic` トークン）**

| モード | Long Break（最暗） | Focus | Short Break（最明） |
| :---- | :---- | :---- | :---- |
| ライト | 0.093 | 0.155 | 0.232 |
| ダーク | 0.218 | 0.340 | 0.509 |

**輝度の順序は両モードで一貫している。** 背景に対するコントラスト比で見ると順序が逆に見えるが（ライトは Short 3.37 ＜ Focus 4.63 ＜ Long 6.63、ダークは Long 4.82 ＜ Focus 6.99 ＜ Short 10.05）、これは背景の明暗が反転しているためであり、色そのものの明るさの関係は変わらない。REQ-COL-021 が維持を求めるのは上表の**絶対輝度**の順序である。

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-COL-020** | **MUST** | 全トークンのコントラスト比と、セッション3色の色覚シミュレーション下 ΔE を検証する自動テストを用意すること。基準は 8.5.3 の役ごとの保証値、および **ΔE 最小 14** とする（8.5.1 の方針値と一致させる）。`-text` の検証は `--bg` / `--bg-sunken` / `--surface` / `--surface-raised` の4面すべてに対して行うこと。 |
| **REQ-COL-021** | **MUST** | セッション3色の**絶対輝度の段差**（Long Break ＜ Focus ＜ Short Break）を両モードで維持すること。3色を同一明度に揃える変更を行ってはならない。 |
| **REQ-COL-022** | **MUST** | macOS メニューバー内ではアクセント色を使用せず、テンプレート画像（単色）とテキストで種別を示すこと。**理由は「色を使えないから」ではない**（使える。`docs/PLATFORM.md`「メニューバー（macOS）」）。**(1) テンプレート画像は地が明暗どちらでも OS が正しく描くと SDK が明言しており、地が可変であっても成立する唯一の手段であること、(2) 色だけに情報を載せないこと**（`accessibilityDisplayShouldDifferentiateWithoutColor`）**の2つによる。** |
| **REQ-COL-023** | **SHOULD** | 「コントラストを上げる」「透明度を下げる」のアクセシビリティ設定に応答し、`-line` を `-graphic` に、`-text-faint` を `-text-muted` に格上げすること。 |

#### 8.5.6 集中表示ビューの配色

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-COL-030** | **MUST** | 集中表示ビュー（REQ-UIX-010）は、システムの外観設定にかかわらず**常にダークモードのパレット**を使用すること。 |
| **REQ-COL-031** | **MUST** | 地は `--bg`（`#13110D`）、タイマー数字は `--text`（`#EBE5DA`、15.04）とすること。セッション種別の色は数字ではなく**進行インジケータ**と種別ラベルに適用すること。**進行インジケータはリングでもバーでもよい** — 集中表示ビューでは数字が短辺の 40% 以上を占めるため（REQ-UIX-010）、横向きでは数字を囲むリングが短辺に収まらない。 |
| **REQ-COL-032** | **SHOULD** | 周囲が暗い場合にタイマー数字を `--text-muted`（7.62）へ落とす減光モードを提供すること。`--text-faint`（ダーク 5.94）より下へは落とさないこと。 |
| **REQ-COL-033** | **SHOULD** | 焼き付き防止の位置移動（REQ-UIX-014）は座標のみを変化させ、色を変えないこと。 |

**背景・理由:** 集中表示ビューを常にダークにするのは、(a) 暗所での長時間注視に適し、(b) ダークモードでは全 `-graphic` トークンが 4.8 以上と余裕があり、(c) 就寝前の利用でも明るさが問題にならないため。

## 9. 設定・プリセット仕様

設定は **プリセットに属する項目**（作業スタイルごとに切り替えたいもの）と、**アプリ全体に属する項目**（どのプリセットでも共通のもの）の2層に分ける。

### 9.1 プリセットの基本仕様

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |

| **REQ-PRS-002** | **MUST** | 常にちょうど1つのプリセットが「有効」であり、その値がタイマー動作に適用されること。有効なプリセットの識別子（`activePresetId`）を状態として保持・同期すること。 |
| **REQ-PRS-003** | **MUST** | プリセットの作成・複製・編集・並べ替え・削除ができること。プリセット数の上限は 10 件とする。 |
| **REQ-PRS-004** | **MUST** | 有効なプリセットを削除しようとした場合は拒否するか、削除前に別のプリセットへ切り替えさせること。プリセットが 0 件になる状態を許容しないこと。 |
| **REQ-PRS-005** | **MUST** | プリセット名は 1〜30 文字とし、重複を許容しないこと。重複判定は、前後の空白を除去し Unicode 正規化（NFKC）と大文字小文字の同一視を行ったうえで比較すること。 |
| **REQ-PRS-006** | **MUST** | プリセットの切り替え・編集は Mac・iPhone のどちらからも行えること。正本は Mac に置く。 |
| **REQ-PRS-007** | **SHOULD** | プリセットにアイコン（SF Symbols）を設定でき、UI 上で判別できること。**プリセットに色を割り当ててはならない**（アクセント色はセッション状態に予約されているため。REQ-COL-012 と同趣旨）。 |

| **REQ-PRS-010** | **MUST** | 初回起動時に上表の`Standard` プリセットのみを作成し、これを有効にすること。追加のプリセットを同梱しないこと。 |
| **REQ-PRS-011** | **MUST** | `Standard` プリセットも編集・複製の対象とすること。ただし全削除を防ぐため REQ-PRS-004 を適用する。 |
| **REQ-PRS-012** | **SHOULD** | 設定画面から `Standard` プリセットを再作成できること。同名が既に存在する場合は連番を付す。連番付与により 30 文字を超える場合は末尾を切り詰めること。プリセットが上限 10 件のときは `presetLimitReached` を返し、作成しないこと。 |
| **REQ-PRS-013** | **SHOULD** | プリセットが1件のみの場合、プリセット切替 UI（REQ-UIX-007）はプリセットの追加への導線として機能させ、切替リストを表示しないこと。 |

**背景・理由:** 同梱プリセットを1つに絞ることで、初回起動時の UI を最小限に保つ。作業スタイルは個人差が大きく、こちらが用意した候補は多くの場合そのままでは使われずノイズになるため、追加は利用者に委ねる。

### 9.5 設定変更の適用タイミング

設定項目を、実行中セッションへの影響で3群に分ける。

| 群 | 対象 | 適用タイミング |
| :---- | :---- | :---- |
| **A. 時間項目** | `workSeconds` / `shortBreakSeconds` / `longBreakSeconds`、およびプリセット切替によるこれらの変化 | **次に開始されるセッションから。** 実行中の `sessionEndAt` を変更してはならない |
| **B. 即時反映（終了時刻に影響しない）** | `autoAdvance`、`notificationSound`、`timeSensitiveNotifications`、`preNotifications`、`longBreakInterval`、`extendSeconds`、およびプリセット切替によるこれらの変化 | **実行中セッションにも即座に適用** |
| **C. 即時反映（識別情報）** | プリセットの `name` / `symbol`、および 9.3 の全項目 | 即座に適用。ただしログには `sessionPresetName`（開始時スナップショット）を用いる |

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-CFG-001** | **MUST** | 設定値およびプリセットの正本は Mac 側に置き、iPhone は表示と変更要求の送信のみを行うこと。 |
| **REQ-CFG-002** | **MUST** | 設定・プリセットの変更は iPhone からも可能とし、変更後は全クライアントへ即座に配信すること。 |
| **REQ-CFG-003** | **MUST** | **A 群**の変更は実行中のセッションに適用せず、`sessionEndAt` を変更しないこと。実行中セッションの長さは `TimerContext.sessionPresetId` が指すプリセットの開始時点の値に固定される（REQ-TIM-004）。 |
| **REQ-CFG-004** | **MUST** | ファイルパスの設定は macOS のセキュリティスコープ付きブックマークとして保存し、アプリ再起動後もアクセス権を維持すること。`bookmarkDataIsStale` が真の場合はブックマークを再生成すること。 |
| **REQ-CFG-014** | **MUST** | `longBreakInterval` の変化（プリセット切替を含む）によって `loopCount` をリセットせず、`nextSessionType` のみ新しい間隔で即座に再計算すること。 |
| **REQ-CFG-015** | **MUST** | **B 群**の変更は、プリセット切替に起因するものを含め、実行中のセッションにも即座に適用すること。通知に影響する項目を変更した場合はローカル通知を再スケジュールすること（REQ-NTF-003）。 |
| **REQ-CFG-016** | **MUST** | 実行中にプリセットを切り替えた場合、`Applies from the next session. The end time of a running session does not change.` と UI で明示すること（**適用範囲を必ず説明する。**「変更しました」で済ませない）。 |
| **REQ-CFG-017** | **MUST** | 実行中に `sessionPresetId` が指すプリセットの A 群項目が編集された場合、`presetEditedDuringSession` を真にすること（REQ-LOG-016）。 |

**背景・理由:** 実行中セッションの長さが設定変更で伸縮すると、事前スケジュール済みのローカル通知との整合が崩れ、「気づいたら終了時刻が変わっていた」という体験になる。長さの変更は「延長」操作に一本化し、A 群は次セッション以降に限定する。B 群は終了時刻に影響しないため即時反映しても安全であり、むしろ「通知音を変えたのに次まで反映されない」ほうが不自然。

### 10.1 共通事項

## 11. 永続化・復帰仕様

### 11.1 永続化

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-PER-001** | **MUST** | Mac は状態が変化するたびに、`TimerContext`・`TaskContext` の選択情報・アプリ全体設定（9.3）・**全プリセットとその表示順**・`activePresetId` をローカルへ永続化すること。 |
| **REQ-PER-002** | **MUST** | Mac アプリの起動時に永続化された状態を復元すること。アプリのクラッシュや再起動でセッションが失われないこと。 |
| **REQ-PER-010** | **MUST** | iPhone は最後に受信した `stateSnapshot` をローカルへ永続化し、起動直後・未接続時にこれを「最後に確認した状態」として表示すること。ただし REQ-COM-012 に従い、この状態からセッションの完了を確定してはならない。 |
| **REQ-PER-011** | **MUST** | iPhone が永続化された状態を表示する際は、取得時刻を併記し、接続が確立して `stateSnapshot` を受信するまで同期中であることを明示すること。 |

### 11.2 セッションの復帰判定

| 要件ID | レベル | 仕様内容 |
| :---- | :---- | :---- |
| **REQ-PER-003** | **MUST** | 復元時の処理は次のとおりとすること。<br>**(a) `committedAt` が非 null（確定済み）** → セッションは完了しているものとして `IDLE` で復元し、ログを再度書かないこと。休憩は REQ-TIM-044 により常にこの経路を通る。<br>**(b) 未確定かつ `sessionEndAt` が未来** → そのまま `RUNNING` で復元する。<br>**(c) 未確定かつ `sessionEndAt` からの経過が猶予（1分）以内** → `FINISHED` のまま復元し、猶予の残り時間を提示する。**これは `WORK` に限る。** 休憩は REQ-TIM-044 により猶予を持たないため、未確定のまま猶予内で復元した場合はその場で完了として確定すること（待たせる理由がない）。<br>**(d) 未確定かつ猶予超過** → `PENDING_DECISION`（`reason: restoredAfterEnd`）へ遷移し、**不在中にセッションが終了していたことと、完了として記録するかの選択**を提示する。応答まで周回数を加算せずログも記録しないこと。 |
| **REQ-PER-004** | **MUST** | `PENDING_DECISION`（`reason: restoredAfterEnd`）が未応答のまま `logicalDate` が変化した場合は、`discard`（中断扱い）として確定すること。**`logicalDayStartHour` の設定変更に起因する `logicalDate` の変化ではこの自動確定を発火させないこと。**このときログに記録する実経過時間は、`sessionStartedAt` から `sessionEndAt` までの正味稼働時間（REQ-TIM-005）とし、放置された実時間を含めないこと。 |
| **REQ-PER-005** | **MUST** | `PENDING_DECISION` の確認は Mac・iPhone の**両方**に表示し、どちらからでも `confirmRestoredSession` で応答できること。**iPhone からの応答は接続が確立している場合にのみ可能である**（REQ-COM-013 により切断中は操作系 UI が無効）。切断中は、Mac 側での確認が必要であることを示すこと。 |
| **REQ-PER-008** | **MUST** | `PENDING_DECISION` の間は、スケジュール済みのローカル通知（終了通知・予告通知）をすべて取り消すこと。既に発火時刻を過ぎているため、再スケジュールは行わない。 |
| **REQ-PER-009** | **MUST** | `PENDING_DECISION` へ遷移した時点で Live Activity を終了させること（8.3）。 |
| **REQ-PER-006** | **SHOULD** | `RUNNING` の間は Mac の**アイドルスリープ**を抑止すること（`ProcessInfo.beginActivity` / `idleSystemSleepDisabled`）。ディスプレイのスリープは抑止しないこと。**蓋を閉じる・メニューからのスリープ・電源設定によるスリープは抑止できない**ため、これらは REQ-PER-003 の復帰処理で扱う。 |
| **REQ-PER-007** | **MUST** | 上記の抑止が効かない経路でスリープした場合でも、絶対時刻基準の設計により復帰時に REQ-PER-003 のロジックで正しく処理されること。 |

**背景・理由:** OS のスリープやアプリ終了は日常的に起こる。絶対時刻を基準にしているため復帰時のズレは生じないが、「不在中に終わっていたセッション」を無条件に完了扱いすると実績が実態と乖離する。判定の境界を猶予と同一（1分）に揃えることで、「猶予内なら通常運転と同じく延長できる／猶予を過ぎたら必ず利用者に聞く」という一貫した規則になる。

## 14. 制約事項

- **1対1接続の原則（MUST）:** システムは「Mac 1台」対「iPhone 1台」のペアリングを前提とする。複数台の iPhone からの同時接続やマルチクライアント制御は考慮しない。REQ-SEC-004 によってこれを担保する。
- **単一の真実（MUST）:** タイマーの進行判定、周回数の加算、タスクのパース結果、設定値の正本は常に Mac 側に置く。iPhone は表示上のカウントダウン補間を行ってよいが、セッションの終了を確定してはならない（REQ-COM-011 / REQ-COM-012）。
- **タスクファイルへの書き込み制限（MUST）:** `Task.md` への書き込みは全面的に禁止する。タスクの追加・編集・完了チェックはすべて**利用者の Markdown エディタ側**で行う運用とする。実績ログファイルへの書き込みのみを例外として許可する。**既存行の改変・削除は行わず、行の挿入のみを行う**（論理日境界の都合上、必ずしもファイル末尾とは限らない）。
- **完全ローカル駆動（MUST）:** 外部クラウドサーバー（Firebase、AWS、APNs 等）への依存を排除し、LAN 環境だけで完結すること。ネットワークアクセスはローカルネットワークに限定する。**この制約の帰結として、Live Activity の push-to-start は採用できず、8.3 の制約を受け入れる。**
- **同一ネットワーク前提（MUST）:** Mac と iPhone が同一の LAN セグメントに存在することを前提とする。VPN 経由やインターネット越しの接続は対象外とする。
- **配布上の制約（MUST）:** iPhone アプリの実機インストールには Apple Developer Program（有償）または無料プロビジョニングプロファイル（7日ごとの再署名）が必要である。無償枠では Time Sensitive 通知（REQ-NTF-005）が**届かない**（2026-08-27 実機確認）。**capability を有効化できるかは確かめていない**（OPEN-007）。配布がソースからのビルドのみである以上、**ソースからビルドする利用者は既定でこの制約下にある**ため、同要件は SHOULD に留める。

**背景・理由:** ネットワーク遅延や認証の手間、サーバー維持コストを排除し、**データが端末の外へ出ない構成**（REQ-NFR-008 / 本章「完全ローカル駆動」）によって、応答性とプライバシー保護を両立するため。
