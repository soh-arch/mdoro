## 問いへの答え

**古い定式化を運んでいるものはあるか — 見つからなかった。**

- 変更前は「プロトコル版が完全一致しなければ**接続は成立しない**」→「同じ版の**中に**現れた知らない値は異常」という定式化。
- 変更後は「プロトコル版が完全一致しなければ**`hello` は拒否される**」→「**成立した接続の上に**現れた知らない値は異常」＋新設の一文（版の違う2台が唯一やり取りするのは `hello` とその拒否までであり、そこで未知の値を受け取っても実害はない）。
- 上記 #4 のコメントは "The line only stands when the protocol versions match exactly" という言い回しを使っており、これは新旧どちらの定式化とも矛盾しない（「接続が成立する」の主語を「版が一致した接続」に絞っている点で新しい方に近い）。他の箇所（#2, #3, #5-9）はいずれも「未知の種別／未知のフィールドは無視する」という、今回の改訂で変わっていない部分だけを指しており、影響を受けない。

一点、指摘ではなく気づきとして: 新設された「版の違う2台が唯一やり取りするのは `hello` とその拒否までであり、そこで未知の値を受け取っても線はそのまま終わるので、数えることに実害はない」という**新しい保証の根拠**そのものを名指しでテストしているコメント・テストは見当たらなかった（#4 のテストは `authFailed`/`command` の未知値を汎用的に検証しているだけで、"版が違う接続" という条件下では書かれていない）。これは「古い定式化を運んでいる」ことの指摘ではなく、単に新設の一文に対応する専用の裏付けがまだ無い、という観察である。

## 問いへの答え

**(a) 版の不一致は `error`（`protocolVersionMismatch`）として出るのか、`authFailed` として出るのか。**

→ **`authFailed` として出るが、`authFailed.code` に版不一致専用のコードは存在せず、`.unknownDeviceToken` として出る。** 根拠:

```swift
// Packages/MdoroCore/Sources/MdoroCore/Protocol/Pairing.swift:121-125
public mutating func authenticate(_ hello: HelloPayload, now: Date) -> Decision {
    // REQ-PRT-004: an incompatible version is refused.
    guard PomodoroProtocol.isCompatible(hello.protocolVersion) else {
        return .reject(.unknownDeviceToken)
    }
```

`ProtocolErrorCode.protocolVersionMismatch`（`error.code` 側のコード）は enum ケースと `displayMessage`（`ProtocolTypes.swift:202-203` "This iPhone and your Mac are running different versions of Mdoro. Update both."）は存在するが、これを実際に送出する箇所は無い（下記コマンドの通り）。

```
$ grep -rn "protocolVersionMismatch" --include=*.swift .
./Packages/MdoroCore/Tests/MdoroCoreTests/FailuresThatReachSomeoneTests.swift:416:  "taskNotFound", "logWriteFailed", "protocolVersionMismatch",
./Packages/MdoroCore/Sources/MdoroCore/Protocol/ProtocolTypes.swift:145:    case protocolVersionMismatch
./Packages/MdoroCore/Sources/MdoroCore/Protocol/ProtocolTypes.swift:202:        case .protocolVersionMismatch:
```
（＝enum 定義・displayMessage・テストの網羅リストにしか現れない。生成箇所は無し。）

なお iPhone 側も `welcome.protocolVersion` を自分で検証していない（`isCompatible` の呼び出しは `Pairing.swift` の1箇所のみ）ため、版不一致の検出は完全に Mac 側の `hello` 処理に一本化されている。また Bonjour の TXT には版番号（`versionKey`）が乗る（`BonjourService.swift:19-21`。コメント: "so a version that cannot speak to this one is visible before a connection"）が、`DiscoveredServer.read(_:)`（`DiscoveredServer.swift:111-118`）は `websocketPort` と `id` しか読んでおらず、**`v` キーは事前フィルタに使われていない**。したがって iPhone は版が異なる Mac にも実際に `hello` を送り、その結果として `authFailed(unknownDeviceToken)` を受け取る経路が現実に生きている（`DiscoveredServer.swift:17-20` のコメント自身がそう明記している: "such a Mac is still listed, and refuses the connection itself on the version check (REQ-PRT-004), rather than vanishing"）。

**(b) `error.code` 表の中に、どの送出箇所からも生成されないコードはあるか。**

→ **ある。表1の「不可」の6件**: `presetNameInvalid`、`invalidFilePath`、`invalidPresetOrder`、`taskFileUnavailable`、`logWriteFailed`、`protocolVersionMismatch`。15コード中6コードが production コードのどこからも `ProtocolErrorPayload` として構築されていない。

**(c) 拒否コードが別の意味のコードで代用されている場合、受け取った iPhone が起こす副作用（保存済みトークンの破棄など）は意図されたものか。**

→ **代用は3件確認できた。うち1件は副作用を伴う。**

1. `protocolVersionMismatch` → `authFailed(unknownDeviceToken)` に代用。
2. `presetNameInvalid` → `settingOutOfRange` に代用。
3. `invalidPresetOrder` → `invalidStateForAction` に代用。

1 について、iPhone 側の受信処理は次の通り:

```swift
// PomodoroMac/PomodoroiOS/Client/MdoroClient.swift:187-192
case let .authFailed(payload):
    status = .failed(payload.code)
    // A token that cannot be used is thrown away.
    if payload.code == .unknownDeviceToken, let serverId = target?.serverId {
        tokens.delete(serverId: serverId)
    }
```

つまり、**正当なペアリング済みトークンを持つ iPhone が、単に版の異なる（例えば更新前後で一時的に版が食い違った）Mac に接続しようとしただけで、`unknownDeviceToken` として扱われ、Keychain に保存された有効なトークンが削除される。** 実際にはトークン自体は無効になっていない（Mac 側の `issuedTokens` は版チェックより前の分岐で弾かれており、トークンの照合すら行われていない）。版問題が解消して同じ Mac に再接続する際は、6桁コードでのペアリングをやり直す必要が生じる。この副作用が意図されたものかどうかは、資料からは判断できない（3.1 の `REQ-COM-003` 条文は「削除された**トークンが記録から消えた**」場合の話をしており、版不一致でトークンを消す話とは別）。

2・3 については副作用は伴わない（`displayMessage` の文言が変わるだけ）が、利用者に見える画面文言が実際の原因とずれる:
- プリセット名を31文字以上にして保存 → 画面には `"That value is outside the range your Mac accepts."`（本来は `presetNameInvalid` の `"A preset name has to be between one and thirty characters."` のはず）
- `reorderPresets` の `orderedIds` が現在のプリセット集合と食い違う → 画面には `"Your Mac did not accept that. The timer is not in a state where it applies."`（本来は `invalidPresetOrder` の `"The new order did not match the presets your Mac holds. Nothing changed."` のはず）

## 割り当て外で気づいたこと（実装せず・起票せず、報告のみ）

- `presetNameInvalid` と `invalidPresetOrder` の代用は A-3 の問い (c) の対象そのものなので上に含めたが、**この2つが「拒否コードの意味の取り違え」として UI 文言の誤りを常に起こす**という一般的な指摘（A-3 の質問文が挙げた「保存済みトークンの破棄」という特定の副作用の外側にある一般論）は、範囲の解釈によっては軸の外かもしれない。念のためここに分離して記載する。提案・是正案は書かない。
- `Preset.isWithinValidRanges()`（`Preset.swift:102-113`）が名前の長さチェックと数値レンジチェックを同一関数に同居させている設計自体（1つの `Bool` 関数が複数の異なる失敗理由を握りつぶしている）は、F-4 / A-3 いずれの軸の直接の対象でもないため、事実の指摘のみに留める。
