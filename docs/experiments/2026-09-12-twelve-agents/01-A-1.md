## 2. 問いへの答え

**成立しません。** 一覧は `hello` とその拒否(`authFailed`)の2本だけではなく、**認証前・接続確定前(`source === connection` が未成立)の状態で `timeSyncPing`/`timeSyncPong` の往復と `heartbeat` の受信が実際に起こり得ます。** これは「受信ハンドラが `hello` の成立前に処理してしまう種別」そのものであり、根拠は以下の実装事実です。

- `handle(_:from:)` 内で `command` と `requestSnapshot` にだけ `guard source === connection else { return }` が明示されている一方、`timeSyncPing` と `heartbeat` の分岐にはこのガードが存在しない(`MdoroServer.swift:222-250`)。
- WebSocket/TCPの接続受理(`accept`)自体にプロトコルバージョンの検査は無く、バージョン検査は `hello` のペイロードに対してのみ `Authenticator.authenticate` の中で行われる(`Pairing.swift:121-125`)。したがって接続自体は版の一致・不一致に関係なく確立し、`hello` を送るかどうか・いつ送るかは相手(=送信側の実装/版)次第であり、受信側(Mac)はそれを強制していない。
- 版が違ってもワイヤ形状(JSONの構造)自体は変わっていないことが `ProtocolTypes.swift:6-9` のコメントで明言されている(「10.2 has no shape change」)。つまり `timeSyncPing`/`heartbeat` は版が違っても互いにデコード可能であり、「版の違う2台の間を実際に流れうる」条件を満たす。

したがって、REQ-PRT-005 の新しい文言「**版の違う2台が唯一やり取りするのは `hello` とその拒否までであり**」は、少なくとも Mac 側の受信ハンドラの実装に照らすと**事実として反例があります**。`timeSyncPing`/`timeSyncPong`/`heartbeat` は、`hello` が一度も送られていなくても(＝拒否すら発生していなくても)成立してしまう経路が実装上開いています。
