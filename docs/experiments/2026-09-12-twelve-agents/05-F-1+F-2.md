**問え: 両立しない組み合わせはあるか**

ある。最も明確なのは **REQ-PRT-005 と REQ-CFG-018（9.1）** の組み合わせである。

- REQ-PRT-005（改訂後、L918）: 「既知のフィールドに載る未知の値は、これに当たらない〔前方互換の免除対象ではない〕」「REQ-ERR-009 の破損メッセージとして扱い、破棄して数えること」。
- REQ-CFG-018（L833）: 「プロトコル経由で範囲外の値を受信した場合は `settingOutOfRange` を返し、値を適用しないこと。」

`updateSettings.changes` に載る `appearance`（`system`/`light`/`dark` の Enum, L840）のような **既知フィールド・許容域外の値** は、両条文が同時に主張する対象になり得る。しかし前者は「黙って捨てて数えるだけ（相手への応答なし）」、後者は「`settingOutOfRange` という具体的なエラーコードを返す（相手への応答あり）」であり、**一つの受信イベントに対して二つの相互排他的な振る舞いを MUST として課している**。どちらを行うべきかを切り分ける記述（「デコードに失敗する値」と「デコードは成功するが業務規則で弾く値」を分ける規定）は本改訂にも周辺条文にも存在しない。

一方、`name`（REQ-PRS-005）や `stableId`（REQ-TSK-036）、`presetId`（`presetNotFound`）はいずれも String 型で、値そのものが型に「載らない」ことがないため REQ-PRT-005 の対象にならず、衝突しない。**衝突は Enum 型の既知フィールドに限られる**が、`appearance` はまさにその条件に該当する。

副次的な指摘として、改訂文末尾の「そこで未知の値を受け取っても線はそのまま終わるので、数えることに実害はない」という結論は、**接続が hello 拒否直後に即座に終わる**ことを前提にしているが、それを直接定める MUST 条文が見当たらない（REQ-COM-005 のハートビート規則が hello 段階にも及ぶかどうかが条文上未確定）。REQ-ERR-009 側との整合は「版違いペアはこの 10 回ロジックに到達しないから無害」という説明で筋が通ってはいるが、その大前提（接続の即時終了）自体が別の MUST で裏付けられていない。

**問え: 意味が変わる記述はどの章にあるか**

- **第9章 REQ-CFG-018**（L833）: 本改訂によって、この条文が想定する「範囲外の値」の一部（Enum 型設定の未知値）が、実は REQ-PRT-005 の言う「新しい相手ではなく異常」に該当し、「値を適用しない」だけでなく「メッセージ全体を破損として破棄し数える」対象でもあり得る、という新たな読み方が生じる。条文の文字面は変わっていないが、**適用範囲の解釈が本改訂前後で変わりうる**。
- **第10章 L1003 の説明文**（「hello そのものの不備...拒否されうる」）: 改訂前は REQ-PRT-005 が「接続は成立しない」という粗い言い方だったのに対し、改訂後は「`hello` は拒否される」と踏み込んだことで、この既存の説明文（`hello` の不備＝未登録トークン・ペアリング窓外・コード誤り・試行超過）と語彙が呼応するようになった。**両者は同じ章内で初めて用語が揃った**とも言えるが、逆に言えば改訂前はこの整合が取れていなかった、ということでもある。
- **第11章 REQ-PER-005/011**: 文言は変わらないが、「接続確立」の境界が本改訂の主張（hello 拒否で線が終わる）に依存する度合いが増した分、この概念が将来どこかで明文化されないままだと、第11章の "接続が確立している場合にのみ" の判定基準も曖昧なままになる。
