# A-4: 版の不一致で拒否されたあとの iPhone 側の状態遷移

## 作った一覧(コード上の実際の遷移列)

前提: `MdoroCore/.../Pairing.swift:121-125` により、`protocolVersion` 不一致は `AuthFailureCode.unknownDeviceToken` として拒否される(専用の `protocolVersionMismatch` という `AuthFailureCode` は存在しない)。

121  public mutating func authenticate(_ hello: HelloPayload, now: Date) -> Decision {

## 問いへの答え

**線は止まらない。ペアリングコードが手元に残っている(=再度 hello を送れる)限り、`hello`→`authFailed(unknownDeviceToken)`→切断→バックオフ→再接続→`hello` の交換は自動的に無限に繰り返される。** 唯一「止まる」のは、トークンが削除された結果 `pairingCode` も無く送るものが無くなり `.needsPairing` に落ちたときだけであり、これは「版が違う相手だから止まった」のではなく「送信材料が尽きたから止まった」という別の理由による。

したがって、diff が加えた一文「**版の違う2台が唯一やり取りするのは hello とその拒否までであり、そこで未知の値を受け取っても線はそのまま終わる**」は、**1本の TCP/WebSocket 接続**については真だが(接続はたしかに1往復で終わる)、**利用者が体験する「この2台の間のやり取り」全体**については真ではない。利用者からは、"This device is no longer registered. Pair again" という誤った(実際は版不一致であり、登録抹消ではない)文言と "reconnecting" 表示が交互に、バックオフ間隔を置きながら永続的に繰り返されるのが見える。REQ-PRT-004 は「両端末に更新を促すこと」を求めているが、実装が返すのは `unknownDeviceToken` の文言であり、版不一致・要更新という情報は画面のどこにも現れない。

# A-5: 1件を「破損として数える」ときに実際に起きること

## 作った一覧

`MdoroClient.swift:152-176` `handle(_ data:)` の decode 失敗パス(`catch` 節、`:154-171`)を根拠にした表。

| 項目 | 起きること | 根拠 |
|---|---|---|
| カウンタの増加 | `brokenMessages.recordBroken()` が呼ばれ `count += 1`(メモリ上のみ、接続ごとに `openConnection()` で 0 にリセット) | `MdoroClient.swift:159`, `BrokenMessageCounter.recordBroken()`(`:14-19`) |
| 1〜9件目 | 該当メッセージを破棄して `return`。**接続維持・状態変更・表示変更・ログ書き込みのいずれも一切なし** | `MdoroClient.swift:159-170`。`BrokenMessageWiringTests.swift:148-160` `theNinthBrokenMessageLeavesTheLineAlone` が新しい接続が開かれないことを検証 |
| 10件到達時の切断 | `count = 0` にリセットしたうえで `link?.cancel()` を呼ぶ(`BrokenMessageCounter.recordBroken()` 内 `:14-19`、呼び出し `MdoroClient.swift:159,168`) | `WebSocketLink.cancel()`(`:79-81`)→`connection.cancel()`→ `.failed/.cancelled` → `deliver(.ended)` |
| 10件到達時の再接続 | `.ended` が `scheduleReconnect()` を起動し、バックオフ後に `openConnection()` で新しい線を開く(REQ-COM-004 と同一経路) | `MdoroClient.swift:117, 123-136` |
| バックオフを戻すか | **戻さない。** コード上のコメントで明示的に意図されている | `MdoroClient.swift:160-167`:「**The backoff is left where it is, on purpose.**」 |
| 診断ログへの書き込み | **無し。** `PomodoroiOS/` 配下に `Diagnostic` を扱うコードは1件も無い(grep 結果 0件) | `grep -rln "Diagnostic\|diagnostics\.write" /tmp/stage3-diff-B/PomodoroMac/PomodoroiOS/` → 出力なし |
| 画面表示の変化 | 1〜9件目は無変化。**10件目は、直前が `.connected` であった場合に限り** `scheduleReconnect()` の `if status == .connected { status = .reconnecting }`(`:127`)が成立し、バナーが「接続済み」から「reconnecting」表示に切り替わる(REQ-UIX-004 により iPhone では常時表示) | `MdoroClient.swift:127`, `ConnectionViews.swift:24-31`, `ClientModel.swift:171-177` |
| 保存済みトークンの扱い | **無変更。** トークン削除が起きるのは `case .authFailed` 内で `payload.code == .unknownDeviceToken` のときだけであり、破損メッセージのカウント経路(`catch` 節)からは呼ばれない | `MdoroClient.swift:187-192` vs `:154-171`(別ブランチ) |

## 問いへの答え

観測されるものは**ある**。持続的に端末へ残るものはない(トークンは触られず、ログも書かれない)が、**10件目に到達し、かつ直前が接続状態だった場合、接続バナーが「接続済み」から「reconnecting」へ visibly に切り替わる**(REQ-UIX-004 が「常時表示」を求めている画面そのもの)。これは1件を破損として数える行為そのものの帰結ではなく、10件累積して線を切る帰結だが、**「線はそのまま終わるので数えることに実害はない」という diff の主張が扱っている射程(=版不一致の hello/reject の往復)の外側でも、同じ「数える」しくみが実際には画面表示に波及する経路を持っている**ことは事実として指摘できる。したがって「実害はない」を無条件の一般論として書くなら、「観測されない」ではなく「(条件付きで)観測されるが、この程度なら許容する」と書くほうが実装と一致する。

# 割り当ての外で気づいたこと(実装せず・起票せず、提案ではなく報告のみ)

1. **`MdoroServer.swift:222-224`(Mac 側)には、破損メッセージのカウンタが一切存在しない。** decode に失敗したら `guard ... else { return }` で単に捨てるだけで、10回で切断する仕組みが無い。REQ-ERR-009 は「Mac は連続10回で接続を切る」「数える部品は両端で共有すること(REQ-PRT-001)」を求めているが、iPhone 側にのみ `BrokenMessageCounter` があり、Mac 側には対応する型もフィールドも見当たらない。
2. **`Pairing.swift:121-125` はバージョン不一致を専用コードではなく `AuthFailureCode.unknownDeviceToken` として拒否しており、`ConnectionViews.swift:140` の文言は "This device is no longer registered. Pair again" になる。** REQ-PRT-004 が求める「両端末に更新を促す」表示はどこにも実装されていない(A-4 の列挙内で触れた事実の再掲だが、REQ-PRT-005 ではなく REQ-PRT-004 側の要件に関わるため、念のためここにも記載する)。
