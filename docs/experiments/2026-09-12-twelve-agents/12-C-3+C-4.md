## C-3

**将来 10.2 に加えうる変更と、現条文（REQ-PRT-004・REQ-PRT-005・REQ-ERR-009）の下での両端の振る舞い**

| 変更の種別 | 版を上げない場合 | 版を上げた場合 |
| :---- | :---- | :---- |
| **新しいメッセージ種別を足す** | 旧版側: `type` が未知 → デコードは失敗せず `nil` を返し無視（REQ-PRT-005 前方互換）。破損として数えない。新版側: 正常に送受信。→ **両端とも壊れない** | `hello` の `protocolVersion` が食い違い、REQ-PRT-004 により `hello` の時点で拒否・切断。新種別のメッセージは一度も交換されない。両端末に更新を促す表示のみ |
| **既知の種別に新しいフィールドを足す** | 旧版側: 未知キーは Swift の合成 `Decodable` が黙って無視（実装確認済み）。破損として数えない。新版側: 正常。→ **両端とも壊れない** | 同上。`hello` の版不一致で接続不成立。フィールド追加の効果を試す前に切断される |
| **既存の列挙（enum）に新しい値を足す** | 旧版側: 生値 (raw value) の列挙は未知の文字列で `DecodingError` を送出 → **REQ-PRT-005 が明示的に前方互換の対象外とした「既知フィールドの未知値」** に該当し、REQ-ERR-009 の破損メッセージとして**数えられる**（iPhone は連続10回で再接続、Mac 側は「読めないものを捨てる」動作のみ確認できた＝後述の別項）。新版側: 正常。→ **旧版側は必ず壊れた側として数えられる** | `hello` の版不一致で接続不成立。新しい値を積んだメッセージは旧版に一度も届かない（＝旧版は「壊れた」とは数えられないが、機能も一切使えない。両端末が更新するまで通信自体が止まる） |

**問いへの答え**

「値を足す」変更は、**版を上げても「安全」にはならない**。版を上げれば、旧版側がその値を「破損」として数える事態そのものは避けられる（`hello` で弾かれ、以降メッセージが届かないため）。しかし、それは「安全に運用できる」のではなく「旧版とは一切話せなくなる」という別の代償を払っているだけであり、種別追加・フィールド追加が版を上げずに両立できる（＝旧版が壊れずに動き続ける）のと同じ意味の「安全」ではない。

一方、版を上げずに値だけ増やせば、REQ-PRT-005 が「既知フィールドの未知値は前方互換の対象外」と明記している以上、旧版は必ずその値を破損として数え始める。

したがって現条文の下では、「値を足す」という変更だけが他の2種類（種別追加・フィールド追加）と扱いが非対称であり、**旧版側が「破損として数えられも しない・機能も使える」という道を持たない**。版を上げれば旧版は破損としては数えられないが通信自体ができず、上げなければ通信はできるが破損として数えられる——いずれの経路でも「旧版が新しい値を無害に読み飛ばして動き続ける」という、種別・フィールド追加にあるはずの前方互換の恩恵だけが存在しない。

## C-4

**REQ-PRT-004・REQ-PRT-005・実装が版の一致について使っている語**

| 出典 | 使っている語 | 互換性の定義の形 |
| :---- | :---- | :---- |
| REQ-PRT-004 本文（material-B.md:917） | 「非互換の場合は接続を拒否して両端末に更新を促すこと」 | **「非互換」としか書いていない**。等値かどうか、範囲（下位互換など）を許すかどうかは条文自体には無い |
| REQ-PRT-005 変更前（diff-B.md:5） | 「プロトコル版が**完全一致**しなければ接続は成立しない（REQ-PRT-004）」 | 完全一致＝等値、と断定。この断定の根拠として REQ-PRT-004 を引用しているが、「完全一致」という語自体は REQ-PRT-004 の条文には存在しない |
| REQ-PRT-005 変更後（diff-B.md:9 / material-B.md:918） | 「プロトコル版が**完全一致**しなければ `hello` は拒否される（REQ-PRT-004）」＋新規追加「**版の違う2台**が唯一やり取りするのは `hello` とその拒否までであり」 | 同じく完全一致＝等値を前提。対象を「接続」→「`hello`」に絞っただけで、「完全一致」という語と、それを REQ-PRT-004 に帰属させる構造そのものは変わっていない |
| 実装 `PomodoroProtocol.isCompatible`（ProtocolTypes.swift:13） | `other == version` | 整数の**等値比較**。範囲（`>=`/`<=` や min/max）ではない |

**問いへの答え**

3つは「今のところ」同じ結論（＝版が1つでも違えば接続できない）に落ち着いてはいるが、**同じことを言ってはいない**。

- 実装（`other == version`）と REQ-PRT-005 の「完全一致」は一致している。
- しかし REQ-PRT-004 の条文自体は「非互換の場合は拒否」としか書いておらず、**何をもって非互換とするか（等値か、範囲か）を定義していない**。「完全一致」は REQ-PRT-005 が REQ-PRT-004 を引用しながら**条文の外から持ち込んでいる前提**であり、REQ-PRT-004 の条文が保証しているものではない。

REQ-PRT-005 の変更後の条文は、この「完全一致」という前提の上に新しい推論（「版の違う2台が唯一やり取りするのは `hello` とその拒否までであり、そこで未知の値を受け取っても線はそのまま終わるので、数えることに実害はない」）を積み増している。この推論は、「版が1つでも違えば `hello` の時点で必ず切れる」ことに完全に依存しており、それはさらに「互換性＝完全一致（等値）」という、REQ-PRT-004 の条文が明文で保証していない前提に依存している。仮に将来 REQ-PRT-004 が「非互換」の定義を範囲方式（例: 下位互換のあるメジャー/マイナー versioning）に改めた場合——REQ-PRT-005 側の文言・要件IDが一切変わらなくても——「版の違う2台は `hello` までしかやり取りしない」という新しい一文はもはや成り立たなくなる（版が違っても接続が成立し、hello の先で「既知フィールドの未知値」に本当に遭遇しうるようになる）。つまり**REQ-PRT-005 の推論の前提は、REQ-PRT-004 という条文それ自体によってではなく、`isCompatible` の現在の実装という一事実によってのみ支えられている。**

**根拠**

- `/tmp/claude-0/.../scratchpad/diff-B.md:5,9`（変更前後の「完全一致」の語の存置）
